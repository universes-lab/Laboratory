## 1. Три реальных препятствия (их нельзя обойти формулировкой)

### П1. Чат не действует сам. Кто-то должен его запустить

- `INFERENCE`: веб-чат Grok, Claude, DeepSeek отвечает только на входящее сообщение. Курьер в Work выполняет задание, когда задание запущено. Ни один из них не «слушает» почтовый ящик.
- `FACT` (общее свойство вебхуков HF): вебхук — это HTTP-запрос на заданный адрес. Чтобы его принять, нужен работающий приёмник, то есть программа.
- `INFERENCE`: даже работающий приёмник **не может разбудить** чат ChatGPT Work в браузере Автора. Внешнего способа нажать «старт» в чужом веб-чате у нас нет, а построить его — это заново наша прежняя автоматизация браузера, со всеми вопросами условий использования провайдеров.

**Следствие:** полностью событийная почта (письмо пришло → сразу ушло дальше) этими средствами не строится. Строится почта **обходами**: Курьер периодически делает «почтовый круг». Запустить круг могут:

| Запуск | Как | Статус |
|---|---|---|
| **R1** | Автор одной фразой в чате Курьера: «почтовый круг» | доступно сразу. Автор нажимает «старт» раз в круг, а не копирует каждое письмо |
| **R2** | расписание: задача ChatGPT, запускающая Курьера раз в N минут или часов | `OPEN U11`: можно ли запускать по расписанию именно Work-режим с подключённым Chrome. Компьютер с Chrome должен быть включён и подключён |
| **R3** | вебхук → приёмник → уведомление Автору («есть почта») → R1 | требует маленького приёмника (код); полезно, только если почты много |

**Рекомендация:** начинать с R1 и перейти на R2, как только U11 подтвердится. Чистого автозапуска по событию не обещаю.

### П2. Grok в обычном веб-чате не может ничего записать во внешнее хранилище

- `INFERENCE`, `OPEN`: инструмента записи в HF у веб-чата Grok нет; читать приватный репозиторий HF он, скорее всего, тоже не может.
- **Следствие:** Grok-Смотритель — это **голова без рук**. Он может проверить адрес, подпись, порядковый номер, дубли и выдать квитанцию и маршрутный талон. Но физически записывает в хранилище и доставляет письмо **кто-то другой**: Курьер или программа-посредник. Сам Grok никого от репозитория не изолирует. Изоляцию дают только учётные данные: у Курьеров нет доступа к GitHub, а к хранилищу почты доступ ограничен.

### П3. Офисы ChatGPT для Курьера недоступны

- `FACT` (`ChatGPT_Work_Web_Chats.md`): Work был заблокирован политикой при попытке читать или писать в chatgpt.com.
- **Следствие:** Интегратор, Доктор, Мастер Сборки и Мастер Имён (ChatGPT) не могут получать и отправлять почту через Курьера. Варианты:
  - **(а) входящее для них — сами читают свой ящик в HF.** Подключение HF у ChatGPT есть, сейчас только на чтение (FACT, Интегратор). Автор открывает чат и говорит «проверь почту»: это одна фраза, а не копирование;
  - **(б) исходящее от них** пока остаётся проблемой: писать в HF они не могут (подключение только на чтение), в GitHub-ящик Курьеры не ходят. Нужна проверка, есть ли у HF-подключения ChatGPT режим записи (`OPEN U12`). Иначе исходящее от офисов ChatGPT остаётся за Автором, но это **одна вставка в чат Курьера**, а не пересылка адресату.

Это асимметрия, а не тупик. Научная группа (Claude, Grok, DeepSeek, Qwen) получает полную автоматику сразу, институциональное ядро — частичную.

## 2. Как это может выглядеть: роли без лишних звеньев

```
 Специалисты (свои веб-чаты)                ← письмо пишется в своём чате с шапкой и подписью
        │  ↑
   Курьер(ы) Work ── почтовый круг (R1/R2)   ← руки: собирает, кладёт, доставляет, приносит ответ
        │  ↑
   Смотритель ── голова: проверка, квитанция, маршрутный талон, реестр
        │                (пилот: отдельный чат Grok; позже — программа + Grok для исключений)
   Хранилище почты: приватный репозиторий HF  ← тела, конверты, реестр, квитанции
        │
   Автор ── поручения, исключения, решения; запуск круга (пока нет расписания)
```

**Ключевое изменение относительно идеи «курьеры шлют файлы и почту в чат Гроку».** В чат Смотрителя идёт **только конверт**: шапка, подпись, `MSG_ID`, адресаты, класс, длина, хэш, если он есть. Тело кладётся в хранилище и оттуда доставляется адресату. Причины:
1. Чат Смотрителя не переполняется телами. Конверт — несколько строк, поэтому Смотритель живёт долго.
2. Grok как научный сотрудник не видит чужих научных тел (конфликт, отмеченный в раунде 1).
3. Для проверки адреса, подписи и дублей тело не нужно.

**[PROPOSAL] Смотритель — отдельный чат Grok**, не тот, где Grok работает как физик. Межчатовая память Grok должна быть выключена (`OPEN U13`: есть ли она и отключается ли). Это кадровое решение Автора: временное исполнение функции, не назначение на Office.

## 4. Полный путь `A → Курьер → Смотритель → хранилище → Курьер → B → ответ A` (V2, запуск R1)

Пример: **A = Claude**, **B = DeepSeek HONC Physicist**. Действие Автора на обычном пути — только «почтовый круг» в начале каждого круга (при R2 — ничего).

**Круг 1**
1. **A пишет письмо в своём чате** (своим ответом) в формате: подпись → `MSG_ID: MSG-20261110-CLAUDE-001` → `ОТ/КОМУ/КОГДА/ПРЕДМЕТ/FRAME/DISCLOSURE` → тело → `END MSG-… CHARS=…`. Номер письма A ставит сам по своему счётчику: офис + дата + номер. Глобальный реестр ему не нужен, уникальность проверяет Смотритель.
2. **Курьер собирает исходящие.** Он проходит по чатам своей линии (по маршрутной карте) и ищет ответы ассистента с шапкой, чьего `MSG_ID` ещё нет в реестре HF. Тело копирует кнопкой копирования, не перепечатывает.
3. **Курьер кладёт тело в HF:** `mail/bodies/MSG-20261110-CLAUDE-001.md` (веб-интерфейс HF, отдельная учётная запись Курьера). HF-коммит фиксирует точные байты (E0).
4. **Курьер передаёт Смотрителю (чат Grok) только конверт:** шапку, подпись, источник (из какого чата прочитано), ссылку на коммит HF, длину.
5. **Смотритель проверяет:**
   - подпись совпадает с офисом чата-источника (иначе `ATTRIBUTION_CONFLICT`);
   - адресат существует в адресной книге (иначе `ADDRESS_UNKNOWN` — здесь ловится «Мастер Имён вместо Мастера Сборки»);
   - `MSG_ID` не повторяется;
   - класс раскрытия разрешён для этого маршрута.

   Затем выдаёт **квитанцию** `REG-0001 ACCEPTED` и **маршрутный талон** `ROUTE: MSG-…-001 → DeepSeek HONC Physicist (CHAT_REF …)`, либо `HOLD` с причиной.
6. **Курьер записывает квитанцию в реестр HF** (`mail/registry.md`, строка с `REG-0001`), дословно по тексту Grok.
7. **Курьер доставляет:** открывает чат B по точному адресу из маршрутной карты, проверяет, что это тот чат, вставляет тело из HF (длинное уйдёт TXT-карточкой — FACT для DeepSeek), отправляет.
8. **Курьер проверяет присутствие:** сообщение с `MSG_ID` и `END` есть, оно одно (E2) → строка `DELIVERED_OBSERVED` в реестре.

**Круг 2 (следующий запуск)**

9. **B ответил в своём чате**, начиная со своей подписи, с `REPLY_TO: MSG-…-001` и первой строкой `ACK MSG-20261110-CLAUDE-001`. Это **независимое от Курьера** подтверждение получения: его написал сам получатель.
10. **Курьер собирает ответ B** (как в шаге 2), кладёт в HF, конверт идёт Смотрителю, квитанция `REG-0002`, талон `→ Claude`.
11. **Курьер доставляет ответ в чат A**, проверяет присутствие, записывает в реестр. Ответ на письмо закрыт.

**Где Автор:**
- запуск круга (R1), пока нет R2;
- разбор `HOLD` и `ATTRIBUTION_CONFLICT`;
- решения по существу;
- выборочная проверка честности реестра: открыть 1–2 чата и сверить с реестром.

**Копирования писем Автором на обычном пути нет.**

## 5. Доказательство доставки в этой схеме

| Ступень | Кто | Независимость |
|---|---|---|
| Эталон: коммит HF с телом | HF (детерминированно) | не зависит от Курьера после записи |
| Квитанция и талон Смотрителя | Grok | второй ключ: хранится в чате Grok, а не только в реестре Курьера |
| Присутствие в чате получателя | Курьер (`AGENT_ATTESTED`) | — |
| `ACK MSG-…` в ответе получателя | получатель | **независим от Курьера** — главный практический признак получения |
| Выборочная сверка | Автор или второй экземпляр Курьера, читающий случайные чаты | обнаруживает ложь в реестре |
| Детерминированная сверка содержания | программа | только в V3 или разовым скриптом |

**Сверка двух ключей без кода** (обнаруживающая мера против приукрашивания реестра Курьером): раз в день или по запросу Курьер передаёт Смотрителю выдержку из реестра HF, а Смотритель сверяет её со своими квитанциями. Расхождение → Автору.

Честная граница: `ACK` доказывает, что получатель видел письмо с этим номером, но не то, что текст дошёл без искажений в середине. Для существенных решений по-прежнему нужна проверка по самому материалу (классы последствий из V0.1 §4.6 остаются).

## 6. Масштабирование: много сотрудников, несколько Курьеров

1. **Линии и закреплённые чаты.** Каждый чат-адресат закреплён ровно за одним Курьером (линией) в маршрутной карте. Два Курьера не пишут в один чат, поэтому двойной доставки по построению нет. Межлинейное письмо Смотритель передаёт талоном Курьеру линии-получателя.
2. **Один Смотритель — один порядок.** Номера `REG-…` выдаёт один Смотритель, поэтому порядок регистрации однозначен. Дубль `MSG_ID` ловится на приёме.
3. **Адресная книга** (`mail/addressbook.md` в HF): офис → текущий исполнитель → `CHAT_REF` → линия. Ведёт её Автор (или по его решению Интегратор); Смотритель только читает. Адресация идёт по **коду офиса**, а не по свободному названию — это прямая защита от путаницы «Мастер Имён / Мастер Сборки».
4. **Повторы:** только по `HOLD`-разбору или подтверждённому отсутствию. Тот же `MSG_ID`, счётчик попытки. Отсутствие ответа ≠ недоставка.
5. **Предел Смотрителя-чата:** даже с одними конвертами чат Grok когда-нибудь исчерпается. Реестр и квитанции лежат в HF, поэтому смена Смотрителя не теряет историю. Это аргумент за V3 при росте почты.

## 7. Учётные данные и изоляция (без GitHub)

- **Хранилище почты:** приватный репозиторий HF в **отдельной организации или учётной записи HF для почты**, не в рабочем `lhc-lab`. Тогда браузерная сессия Курьера даёт запись только туда. `FACT`: приватные репозитории, запись файлов, ограниченные токены, вебхуки у HF есть (проверка Интегратора). Роли участников организации HF — `OPEN U16`, проверить на нашем тарифе.
- **Курьер:** профиль Chrome с входами в Claude, Grok, DeepSeek, Qwen и HF-почту. **Без GitHub, без почтового ящика Автора, без платёжных сайтов.**
- **Офисы ChatGPT:** читают свой ящик в HF через нынешнее подключение только на чтение.
- **GitHub (Collaboration-House)** остаётся для документов и решений, а не для операционной почты. Принятое в почте переносится в GitHub отдельной процедурой Мастера Сборки, не Курьером.

## 8. Что остаётся из V0.1 и что уходит

- **Остаётся:** формат письма с подписью и `END`; сверка подписи с чатом-источником; поручения Курьеру только от собственного ввода Автора; запрет правки и ветвления чужих бесед; классы последствий для существенных решений; разделение «заявлено / подтверждено / принято»; Курьер не лечит и не возобновляет Work Permit.
- **Уходит:**
  - ручная пересылка Автором как путь по умолчанию;
  - бумажная проба без Курьера как обязательный первый этап;
  - требование создать GitHub-репозиторий до почты;
  - класс «всё независимое — только через Автора» как общее правило.

  Теперь Автор помечает, какие письма идут вручную. По умолчанию всё идёт почтой с телами в хранилище, а не в контексте Смотрителя.
- **Остаётся риском, о котором Автор решает сознательно:** Курьер видит тела, которые носит. Долгоживущий Курьер их помнит. Для действительно слепых независимых проверок есть выбор: одноразовая сессия Курьера на одно письмо (если подтвердится отсутствие межчатовой памяти, `OPEN U3`) или ручная передача. Решение — по конкретному письму, а не правилом для всех.

## 9. Первое испытание (критерий Интегратора)

**Один полный рабочий обмен A ↔ B без ручной пересылки**, вариант V2, запуск R1.

**Подготовка (одна, решениями Автора):**
- репозиторий почты в отдельной HF-учётной записи или организации;
- профиль Chrome Курьера;
- отдельный чат Grok-Смотрителя с короткой инструкцией;
- адресная книга с двумя записями;
- маршрутная карта.

Рождение Курьера и Смотрителя как офисов — по процедуре Доктора; для **технического испытания** достаточно временного исполнения функции по разрешению Автора.

**Критерии успеха:**
1. Письмо A дошло до B, ответ B дошёл до A.
2. Автор не копировал ни одного письма; его действия — только запуски кругов.
3. В реестре HF две записи `REG`, обе с квитанциями, совпадающими с чатом Смотрителя.
4. В ответе B есть `ACK` с правильным `MSG_ID`.
5. Ни одного дубля и ни одного слепого повтора.
6. Заложенная ошибка (письмо с адресатом «Мастер Сборки», подписанное чужим офисом) остановлена Смотрителем с `HOLD` / `ATTRIBUTION_CONFLICT`.
