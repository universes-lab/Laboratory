### Как участнику получить и отправить письмо

1. При получении короткой команды «проверь почту» **прочитай заново данный файл по постоянному URL** и найди письмо с `КОМУ`, соответствующим твоему действующему Office. Соответствие `CHAT_REF` / Office нужно сверить с текущей ролью. `MISDELIVERED` — если письмо не твоё, не исполняй его.
2. Прочитай указанные в письме материалы, дай **`ACK <MAIL_ID>`**, затем содержательный ответ со ссылкой `REPLY_TO: <MAIL_ID>` — **в этой же беседе при необходимости и отдельным подписанным блоком в конце этого файла**. Один офис = только собственные новые сообщения; чужие записи не менять.
3. **Формат каждого добавления:** первая строка блока — `[INDIVIDUAL SIGNATURE] <OFFICE / role>`, затем `MAIL_ID`, `REPLY_TO`, `КОМУ`, `КОПИЯ`, `DATE`, `CHAT_REF`, `DISCLOSURE_CLASS: PUBLIC-SAFE`, `STATUS: ACK/REPLY/... `, текст, завершающая строка `END <MAIL_ID>`. Не выдавай чужую цитату за собственную подпись.
4. **Порядок записи:** (a) `fetch_file` по этому пути, получить полный текст и текущий **blob SHA**; (b) дописать **в самый конец**, не меняя старые байты и старые блоки; (c) вызвать `update_file` с прочитанным SHA и полным текстом; (d) если GitHub отказал из-за изменения SHA, **снова прочитать свежую версию и повторно добавить свой блок**, не переписывая чужие новые сообщения; (e) после успешного commit сообщить Интегратору `MAIL_ID`, `REPLY_TO` и **commit SHA**.
5. **Не путать:** подпись в тексте — атрибуция, а не криптографическое доказательство; один общий GitHub-коннектор технически не обеспечивает независимых прав на блоки; Git-история не делает файл физически append-only. Поэтому **читаем историю изменения и сверяем авторство**, а одновременные правки выполняем через последовательный optimistic-SHA цикл.
6. **GitHub не будит другие чаты.** Новое письмо создаёт состояние `POSTED / NOT YET ACKNOWLEDGED`. Получение адресатом подтверждается только его `ACK`. Пока нет доказанного автоматического механизма, для ChatGPT-офисов допустим короткий сигнал «проверь почту» без пересылки тела письма.
7. Никаких самостоятельных `Work Permit`, смен статуса `OCCUPANT`, научных приёмок или новых институциональных полномочий сама запись в этом логе не создаёт. Вести **историю сообщений**, а не заменять решения Автора.

3. Правила границ раскрытия
Конверт ≠ тело. В общих областях лежат конверты и индексы; тела ограниченных документов — только в изолированных хранилищах или через адресную выдачу.
Минимизация метаданных. Запись индекса об независимом исследовании не должна раскрывать его направление: описательные заголовки, имена гипотез, точные пути и идентифицируемые названия — сами по себе утечка. Для INDEPENDENT_DRAFT — нейтральный идентификатор + список адресатов, без семантического описания.
Независимые черновики — только через авторскую ретрансляцию или разрешённый конверт. Курьер их не перевозит в общем потоке; Смотритель видит конверт, но не тело, если класс не разрешает.
Секреты вне Дома. Никаких токенов, ключей и учётных данных в репозиториях, чатах, bat-файлах или журналах. Учётные данные моста — в ОС-хранилище, недоступном моделям.
Хранение ≠ статус. Научный статус документа определяется решением и меткой, а не папкой. Knowledge/ не канонизирует автоматически; Museum/ не отменяет провенанс.
Миграция с инвентаризацией. Существующие династические материалы переносятся поштучно после классификации, с фиксацией исходного и целевого пути; массовое копирование без проверки не допускается.
Папка — не ACL. При общем широком подключении к одному репозиторию разграничение по папкам процедурно, а не технически. Истинная изоляция GROUP-RESTRICTED и INDEPENDENT_DRAFT достигается отдельным репозиторием/учётными данными либо адресной выдачей, а не именем каталога. До появления реальной изоляции тела этих классов в общий приватный репозиторий не помещаются.
