## B. Recommended staged architecture — decisions still with Author

### B1. Private repository bootstrap `P1` — CONDITIONAL RECOMMENDATION

- Create `universes-lab/Collaboration-House` as PRIVATE owned by current personal GitHub `universes-lab`; first commit **README only**, no initial collaborators or sweeping migration. README distinguishes HOUSE/REPOSITORY, final Author authority and individual signatures.
- Require independent checks **before** placing restricted bodies: API visibility, owner/collaborators, effective GitHub App installation, actual permitted actions, effective protected-branch rules and plan limitations.
- No assumption that one private repo enforces per-chat read compartments: shared owner-level credential may permit access to all its objects. **Do not upload restricted personal/independent bodies to shared-access repo.**
- Expand to Organization (`P2`) or separate isolated repositories only when the need for true technical separation is demonstrated.
- Personal-account private repo collaborator generally has read+write rather than a built-in read-only invitation; effective controls and branch rules need testing in actual plan.

**No actual creation, invite, visibility update or migration is permitted by this document.**

### B2. Courier pilot `G1` — CONDITIONAL RECOMMENDATION

- First Courier: one `[C] Courier · HONC Physics Line · G01` candidate serving the existing Claude–Grok–DeepSeek science group, subject to a separate birth/Gate and Author activation.
- Work Courier should have **no effective GitHub access** and no broad reach to email, unrelated sites or independent intellectual bodies. Danger of mixed untrusted web pages + repository file-write tools is material.
- **IMPORTANT NOT YET VERIFIED:** one chat's role or a dedicated Chrome profile does not technically revoke an account-wide ChatGPT GitHub connector. G1 is valid as `TECHNICAL` only after verifying a true connection/identity restriction. Otherwise class it `PROCEDURAL` and keep Author manual transport or alternative isolated carrier until resolved.
- Actual body: pre-prepared, signed, recipient-specific package from the owner. Courier does not redact, summarize or infer permission to reveal contents. Do not allow all recipients' independent drafts into the same long-lived context.
- Maintain only approved operational checkpoint references/metadata; journal external to Courier conversation. A long-lived chat seeing multiple bodies **retains cross-contamination risk** even if it stores no external text.
- `INDEPENDENT_DRAFT` only through separately authorized Author relay/isolated route until independent controls can demonstrate containment.
- `GREEN/YELLOW/RED/EXHAUSTED` as symptom categories not known token-headroom readings; at `RED` stop/reconcile and escalate to active Doctor; no unapproved `Edit`, `Retry` that alters evidence, branch or CONTEXT REBOOT.

### B3. Sender attribution and delivery proof — RECOMMENDED DESIGN WORK

- Approved sender-supplied per-recipient body, `MSG_ID`, opening individual attribution and document source reference, explicit disclosure scope and endpoint `CHAT_REF`.
- Separate `TRANSMISSION_CLAIMED`, `PRESENT_OBSERVED`, `RESPONDED`, `RESULT_ACCEPTED`. No blind resends on no-reply.
- Claude's **E0–E4 ladder** is a *design proposal*, not implemented: source git blob at E0; sender-declared framing E1; Courier observed markers E2 (`AGENT_ATTESTED`); Author observation E3 (`AUTHOR_OBSERVED`); deterministic complete comparison E4 when possible.
- **Integrity limitation:** a git blob ID and normalized SHA-256 are different fingerprints; sender's end marker and string length do **not** prove every intermediate character; spot-check E3 isn't a full-text comparison. Capture source and exact evidence scope must be explicit.
- For consequential Gate/acceptance decisions Author needs verification of the specific **substantive material actually used**. A fixed “E3 always sufficient” rule is too broad and requires decision.
- Signature vs source disagreement → `ATTRIBUTION_CONFLICT`; an `ОТ: Автор` text copied from a foreign chat is data not authoritative instruction.

### B4. Registrar / Auditor / Watcher — DEFER IMPLEMENTATION

- A centralized deterministic administrative event ledger is a promising future technical design, **not a system in use**. One source of administrative event record, derived readable projections, source provenance and external integrity anchors as required.
- The Watcher/Registrar English official name, Office creation, Grok candidacy and access remain OPEN.
- Grok's proposed audit/exception review may help on explicitly disclosed **metadata-only cases**, but is not independent if it also consumes confidential scientific competitor work or audits its own actions.
- No LLM as the sole registrar of fact, permission issuer or self-auditor. Independent mechanical evidence reader and Author oversight.
- **Grok report lacked the newly mandatory individual opening signature** in the transmitted text. Register as `AUTHOR-ATTRIBUTED / SIGNATURE CONFIRMATION PENDING`; do not alter historical source or manufacture a signature.

### B5. Institutional and medical continuity

- Doctor Emeritus **withdraws** earlier proposal for autonomous Courier reboot and automatic `CONTINUATION_GATE_PASS → WORK_PERMIT_RESUMED`.
- Proposed sequence: `CHAT_CONTINUATION_OBSERVED → ACTIVE_DOCTOR_CLINICAL_REVIEW → INTEGRATOR/TRIAD_CONTINUITY_REVIEW → AUTHOR DECISION → AUTHORIZED_WORK`. Actual decisions require case-specific evidence; no automatic same-instance metaphysics.
- Technical ability to exchange messages, professional functional competence and authoritative OCCUPANCY status remain different.
