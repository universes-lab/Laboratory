## 1. Слои и их состояния

Контракт различает пять слоёв. Каждый слой имеет собственный идентификатор и собственное состояние; состояние одного слоя не выводится из другого.

| Слой | Что это | Идентификатор | Пережитое событие, при котором слой **обязан сохраниться** |
|---|---|---|---|
| SEAT | должность в рабочем пространстве | `seat_id` (задаётся институционально; **не** выводится из URL, провайдера, профиля) | всё ниже |
| OCCUPANT | конкретная беседа/экземпляр модели, занимающий кресло | `occupant_ref` = (`provider`, `conv_id`); `conv_id` — идентификатор беседы из адреса, без токенов | перезапуск браузера, потеря сессии, смена хоста |
| SESSION | авторизованный persistent-контекст | `profile_id` | перезапуск браузера |
| TRANSPORT | вкладка/соединение/управляющий канал | `handle_id` (эфемерный) | ничего: пересоздаётся |
| BINDING | запись «кто в каком кресле и на каком основании» | `binding_id` + `authority_epoch` | всё, кроме явного события succession |

**1.1 Состояния (закрытые списки).**
- SEAT: `VACANT` · `BOUND` · `SUSPENDED` (автоматизация приостановлена) · `RETIRED`.
- OCCUPANT (наблюдение): `UNVERIFIED` · `VERIFIED` (conv_id подтверждён при последнем подключении) · `UNREACHABLE` · `REPLACED` (только через succession-событие).
- SESSION: `AUTHENTICATED` · `EXPIRED` · `CHALLENGE` (CAPTCHA/2FA/подтверждение) · `ABSENT` · `UNKNOWN`.
- TRANSPORT: `DETACHED` · `ATTACHED` · `DEGRADED` · `LOST`.
- Режим автоматизации кресла: `M0` view-only · `M1` observe/extract · `M2` assisted-manual · `M3` compose-draft · `M4` auto-send; индикатор: `AUTOMATION=OFF|PAUSED|ACTIVE`.
- Генерация в беседе (наблюдение, не состояние кресла): `IDLE` · `GENERATING` · `UNKNOWN`.

**1.2 Матрица «событие × слой»** [MUST — ожидаемое поведение, проверяется в WS-1/WS-2].

| Событие | SEAT / BINDING | OCCUPANT | SESSION | TRANSPORT |
|---|---|---|---|---|
| Штатное закрытие/открытие браузера | без изменений | без изменений, перепроверяется | сохраняется (если cookies живы) | пересоздаётся |
| Kill процесса | без изменений | без изменений, перепроверяется | сохраняется или `UNKNOWN` | `LOST` → новый |
| Истечение авторизации | без изменений; режим → не выше M0 до входа | `UNVERIFIED` | `EXPIRED`/`CHALLENGE` | без изменений |
| Замена беседы (новая вместо старой) | **новое** BINDING, новая `authority_epoch` | `REPLACED` + новый occupant | без изменений | без изменений |
| Смена хоста (H-A↔H-B↔H-C) | без изменений; фиксируется в паспорте | перепроверяется | **может быть утрачена** (профили не обязаны быть переносимы) | новый |
| Перезагрузка среды | без изменений | перепроверяется | как при kill | новый |
| Видимая смена метки модели в той же беседе | без изменений; флаг `model_label_changed` | `VERIFIED` + флаг | без изменений | без изменений |

[NOTE] Является ли смена метки модели сменой жильца — институциональный вопрос (Автор/триада), не WS-0. WS-0 требует лишь, чтобы она не оставалась незамеченной.

## 2. Статусы восстановления (вердикт по креслу после рестарта)

Пять верхнеуровневых статусов; **дельта** — не отдельный статус, а признак `delta=true|false` у `RECOVERED`. (Согласование с планом v1.1 §4.3: `RECOVERED_WITH_DELTA` ≡ `RECOVERED` + `delta=true`.)

| Статус | Определение |
|---|---|
| `RECOVERED` | Кресло наблюдаемо, беседа та же (`conv_id` совпал), вся история «до» присутствует без изменений (цепочка хэшей совпала), а всё новое объяснено (`delta=true` допускается только при объяснённой дельте). |
| `AMBIGUOUS` | Наблюдать можно, но однозначно решить нельзя: неполная загрузка истории, неразрешённый статус отправки, неатрибутированная дельта, несопоставимые пути извлечения. **Никогда не округляется до RECOVERED.** |
| `LOST` | Авторизация в порядке (или подтверждена человеком), но беседа недоступна/удалена/не открывается по сохранённому адресу. |
| `NEEDS_HUMAN` | Наблюдение невозможно без человека: `EXPIRED`/`CHALLENGE`, конфликт двойного владения, неожиданный диалог, запрет автоматизации. Вердикт откладывается. |
| `MISMATCH` | Адрес открывается, но это **не та** беседа или история «до» не совпадает с историей «после» (иной `conv_id`, иная цепочка хэшей). Тревога: возможна молчаливая подмена. |

**2.1 Порядок применения правил (первое сработавшее побеждает).**
1. Нет pre- или post-снимка, или снимок невалиден → `AMBIGUOUS` (причина `NO_EVIDENCE`).
2. `SESSION ∈ {EXPIRED, CHALLENGE}` или обнаружено двойное владение или режим автоматизации запрещает наблюдение → `NEEDS_HUMAN`.
3. Беседа не открывается при `SESSION=AUTHENTICATED` → `LOST`.
4. `conv_id_post ≠ conv_id_pre` → `MISMATCH`.
5. `extraction_path_post ≠ extraction_path_pre` (DOM против API) при отсутствии пересчёта по одному пути → `AMBIGUOUS` (`PATHS_NOT_COMPARABLE`). [NOTE: хэши сопоставимы только внутри одного пути и одной версии нормализации.]
6. `history_complete_post = false` → `AMBIGUOUS` (`HISTORY_INCOMPLETE`).
7. Цепочка хэшей первых `n_pre` сообщений «после» ≠ `chain_pre` → `MISMATCH` (`PREFIX_CHANGED`; причина подсказкой, не выводом: правка/регенерация/удаление/другая беседа).
8. Есть неразрешённая отправка (`send_status` ∈ {`INTENDED`, `AMBIGUOUS`}) → `AMBIGUOUS` (`SEND_UNRESOLVED`).
9. Есть дельта (`n_post > n_pre`): если каждое новое сообщение атрибутировано (ответ на `send_nonce`, либо записанное человеческое действие) → `RECOVERED`, `delta=true`; иначе → `AMBIGUOUS` (`UNATTRIBUTED_DELTA`).
10. Иначе → `RECOVERED`, `delta=false`.
Вердикт всегда сопровождается: списком сработавших правил, ссылками на снимки, версиями паспорта. [MUST]

**2.2 Статус отправки (для WS-3; схема фиксируется сейчас, чтобы не менять снимки позже).** `send_status`: `NONE` · `INTENDED` (намерение записано до действия) · `CONFIRMED_PRESENT` (nonce найден в беседе) · `CONFIRMED_ABSENT` (история полна, генерация `IDLE`, выдержан заранее заданный интервал ожидания — значение фиксируется до серии) · `AMBIGUOUS`. [MUST] Повтор отправки при `AMBIGUOUS` без человека запрещён.

**2.3 Разрешение AMBIGUOUS/NEEDS_HUMAN.** Только человеком; записывается отдельным полем (`resolution`, `resolved_by`, `resolved_at`, основание); исходный вердикт не перезаписывается. [MUST]

## 4. Критерии отсутствия молчаливой подмены

Каждый критерий проверяем; нарушение любого — провал сценария независимо от остальных результатов.

- **SS-1** Любое изменение BINDING/жильца есть **явное событие** с причиной и автором; побочным эффектом перезапуска оно быть не может.
- **SS-2** `seat_id` не зависит от URL, профиля, названия и модели; их смена не меняет `seat_id`.
- **SS-3** При каждом подключении сравнивается `conv_id`; совпадение заголовка/адреса без совпадения `conv_id` и цепочки хэшей — не подтверждение.
- **SS-4** Вердикт не выдаётся без обоих снимков; отсутствие данных даёт `AMBIGUOUS`, не `RECOVERED`.
- **SS-5** Вердикт не повышается автоматически (`AMBIGUOUS`/`NEEDS_HUMAN` → `RECOVERED`); только человеческое `resolution` (§2.3).
- **SS-6** Нет молчаливых повторов отправки; каждое действие автоматизации записывается как «намерение» до и «результат» после.
- **SS-7** Смена хоста, версии runtime, пути извлечения, версии нормализации фиксируется и делает сравнение недействительным без пересчёта.
- **SS-8** Новый жилец не наследует полномочия: новая `authority_epoch` требует отдельной записи о предоставлении; её отсутствие = нет полномочий.
- **SS-9** Человеческие действия (сообщение, отправленное вручную) обнаруживаются и атрибутируются, а не затираются моделью состояния.
- **SS-10** Видимая смена метки модели/варианта интерфейса не остаётся незамеченной (`flags`).

## 6. STOP-условия (действуют для WS-0 как документальной работы и переходят в WS-1+)

Остановка и возврат Интегратору при любом из:
1. Появилась необходимость запустить код, открыть браузер, войти в аккаунт, коснуться живых чатов Коллаборации — в рамках WS-0 это запрещено.
2. Обнаружено, что вердикт нельзя вычислить из полей §3 без чтения текста сообщений (нарушение границы L1/L2).
3. Два ревьюера получают разные вердикты на одном тестовом векторе (§7) — правила неоднозначны.
4. Потребовалось выбрать хост, браузер, драйвер или хранилище, чтобы завершить контракт.
5. В артефактах контракта оказались секреты, cookies, токены или реальные тексты чатов.
6. Для WS-1+: любой из STOP из плана §6.2 (предупреждение/блок аккаунта, доступ к живым чатам, BODY/canary в запрещённом месте, отправка в режиме M0/M1, правка критерия посреди серии).

## 8. Граница WS-0 → WS-1

**WS-0 считается завершённым**, когда: (1) контракт прочитан DeepSeek с точки зрения технической исполнимости и Интегратором с точки зрения согласованности с планом; (2) двое независимо получают одинаковые вердикты на всех векторах §7, расхождения устранены правкой контракта, а не векторов; (3) открытые пункты [OPEN] перечислены; (4) в артефактах нет секретов и реальных текстов.

**Что WS-0 НЕ даёт и что нужно для перехода в WS-1:** отдельное разрешение Автора на WS-1; решение о том, кто и как строит fixture (синтетический «провайдер») и какой набор хостов сравнивается (в WS-0 не обсуждается); выделенное тестовое окружение (DTE) и его владелец; паспорт версий каждого хоста (D1); пилотные параметры (N=10 × 4 вида × 2 кресла, D5). Контракт не создаёт задач для Samurai.
Для WS-2/WS-3 дополнительно, **до** соответствующей ступени: P-B1 (вход/чтение через автоматизацию), P-B2 (отправка), P-B3 (внутренние API) — раздельные разрешения Автора; решение о допустимости пути для production принимается позже, на данных.

## 9. Учёт согласованных D1–D8
D1 паспорт версий хоста → поле `host_versions_ref`, §8 · D2 P-B1/2/3 → §8 · D3 канал управления → требование окружения плана §3.2 (контракт его не дублирует) · D4 старение runtime → `flags.ui_variant_changed`, паспорт · D5 пилот → §8 · D6 оракул и выборочная проверка → векторы §7 дают оракул для автоматической сверки; выборка — по плану §6.1 · D7 T6.x по ступеням → §3 (только L0/производные) · D8 независимость от смоук-плана → контракт не содержит legacy-запусков.
