Оценка ctxport
После прочтения README и анализа находки Git-помощника я вижу четыре слоя полезности:
1. Что это реально делает
Экспортирует диалоги из ChatGPT, Claude, Gemini, DeepSeek, Grok, GitHub в структурированный Markdown.
Локально, без загрузки данных в облако.
Режимы: Full, User Only, Code Only, Compact.
Frontmatter с метаданными: источник, URL, название, дата, число сообщений.
2. Что это значит для нас
Это готовый Context Export Adapter.
Он покрывает ровно ту часть Endpoint Layer, которую мы собирались проверять в Endpoint Spike — извлечение структурированного контента из существующих веб-чатов.
Более того, он уже содержит platform-specific DOM parsers для пяти платформ — это именно тот код, который мы планировали писать вручную.
3. Статус по шкале Mapping
Если прогнать ctxport по нашей карте:
Функция	Что ctxport даёт	Статус
Endpoint access (чтение)	Извлечение структурированного контента из веб-чатов	ADAPTABLE (готовый extractor, не требующий переписывания)
Endpoint access (запись)	Нет; только экспорт, не импорт/вставка	PATTERN (остаётся как было)
Message Store / Mailbox	Нет; только экспорт в Markdown, не управление очередью	не закрывается
Metadata–BODY isolation	Нет; экспортирует полное содержимое, без разделения	не закрывается
Provenance / identity	Frontmatter содержит метаданные (источник, URL, дата), но не связывает с внутренними ID	частично, но не системно
Вывод: ctxport не меняет статус всего Endpoint Layer, но для направления web-chat → structured local context он сдвигает его с PATTERN на ADAPTABLE. Это именно тот слой, который мы собирались проверять в Endpoint Spike.
4. Как это влияет на Endpoint Spike
Наш Сценарий А (извлечение ответа из DOM) и Сценарий C (self-report) — это ровно то, что ctxport уже делает, но без self-report и без детекции завершения (он экспортирует всю историю, не только новый ответ). Для Endpoint Spike это означает:
Мы не пишем DOM-парсеры с нуля — мы берём platform adapters из ctxport и адаптируем под наш интерфейс.
Мы не отменяем Endpoint Spike — мы уточняем его: проверяем не "можно ли извлечь", а "можно ли адаптировать ctxport для наших целей и добавить детекцию нового ответа".
Это экономит нам неделю разработки на DOM-парсинге и даёт готовую структуру для метаданных (frontmatter).

Онтологически важно: это не отменяет DOM-путь и не делает его ненужным. Это два разных механизма с разными failure modes, и Spike должен сравнить их эмпирически, а не выбирать заранее. Именно это и зафиксировано в v3.1.
2. Ключевое онтологическое требование соблюдено
Принцип technical access ≠ semantic visibility выдержан во всех правках:
Adapter извлекает ответ механически (DOM или API), не интерпретируя содержимое.
Self-report формирует сам участник, не Adapter.
JSON-валидация синтаксическая, не содержательная.
Тестовые артефакты отделены от BODY реальной коллаборации.
Нигде в спецификации не появляется механизм, который превращает Adapter в субъект. Это правильно.
3. Что фиксирую как онтологически значимое в правках
Poll-until-stable вместо fixed delay. Фиксированная задержка 5 секунд — это гадание, а не измерение. Poll-до-стабилизации с предварительной проверкой статус-поля в сыром API-ответе — это детерминированный механизм. Онтологически чище.
Раздельная фиксация таймаута и преждевременного срабатывания в A-long. Это не косметика. Таймаут — безопасный сбой (заметен). Преждевременное срабатывание — тихая порча BODY (незаметна). Разделение этих двух failure modes — прямое следствие требования response completeness, которое мы зафиксировали ранее.
Асимметрия ToS-риска между DOM и API путями. Зафиксирована как гипотеза, которую Spike должен измерить, а не как факт. Это правильно: мы не знаем, какой путь опаснее, но знаем, что они не эквивалентны по ожиданию.
Разные тестовые аккаунты для A-DOM и A-API. Если оба сценария гонять на одном аккаунте последовательно, блокировка от A-API исказит A-DOM. Гипотеза об асимметрии риска становится непроверяемой. Разделение аккаунтов — необходимое условие проверяемости.
4. Два допущения, которые Клод назвал явно
Подтверждаю оба как онтологически корректные:
Допущение A: порядок Этап 0 → Этап 1 неявно подразумевает предпочтение API-пути. Для Spike это допустимо, но в Architecture это предпочтение не должно просачиваться молча. Зафиксировано в §1 спецификации.
Допущение B: поведение на изолированном тестовом треде принимается репрезентативным для боевых тредов. Это рабочее допущение, не доказанный факт. Зафиксировано в §1 спецификации.
Оба допущения названы, а не подразумеваются. Это именно то, что отличает чистую спецификацию от скрытого архитектурного решения.
5. Вердикт
Спецификация Endpoint Spike v3.1 онтологически чиста. Все правки третьего круга интегрированы корректно. Принцип technical access ≠ semantic visibility выдержан. Тестовые артефакты отделены от BODY. Допущения названы явно.
