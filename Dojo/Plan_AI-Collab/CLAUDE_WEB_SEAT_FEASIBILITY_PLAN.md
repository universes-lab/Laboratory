## 0. Сводка в шести строках

1. Проверяется один примитив: **persistent browser context → institutional seat → существующий долгоживущий чат → restart/recovery**, затем продолжение Endpoint Spike v3.1: **address → send → detect completion → extract → recover**.
2. План разбит на четыре независимо разрешаемые ступени: **WS-0** (бумага, без сети), **WS-1** (механика хоста на локальном синтетическом «провайдере», без живых сервисов), **WS-2** (живые тестовые аккаунты, только чтение, без отправки), **WS-3** (Spike v3.1: отправка и т. д.). Каждая ступень получает отдельное разрешение Автора.
3. Три кандидата-хоста (внешний профиль / встроенное Chromium-окружение / гибрид) сравниваются по критериям, победитель **не назначается**.
4. Любая проверка, затрагивающая логины, сообщения, CDP/внутренние API, kill/restart профиля, — **только в выделенном тестовом окружении** и **не** на живых чатах Коллаборации.
5. «Рабочее пространство без автоотправки» — самостоятельный режим с собственными тестами; ручной fallback видим всегда и проверяется инъекцией отказов.
6. Блокеры: ревизия HF-снапшота не зафиксирована (§2.3, §9); `requirements.txt` нечитаем (относится к смоук-плану DeepSeek, не к этому).

## 1. Цели и не-цели

### 1.1 Цели
- G1. Выяснить, **можно ли** отделить постоянное кресло (SEAT/OFFICE) от браузерной сессии и от конкретного жильца (OCCUPANT) так, чтобы замена нижележащего слоя не теряла и не подменяла верхний.
- G2. Получить **измеренные** свидетельства о том, какие хостинг-схемы вообще держат несколько авторизованных persistent-контекстов и переживают перезапуск.
- G3. Определить **минимальный набор наблюдений**, достаточный, чтобы после перезапуска утверждать: «это то же кресло, тот же чат, вот что изменилось».
- G4. Проверить, что рабочее пространство полезно **без** автоматической отправки сообщений, и что ручной fallback всегда виден.
- G5. Проверить разделение «технический доступ к BODY» / «право читать его по смыслу» на уровне наблюдаемых артефактов (журналы, скриншоты, трассы, дампы), а не только на уровне декларации.
- G6. Для каждого провайдера собрать отдельные данные по двум путям (DOM/UI и внутренний API через авторизованный контекст): что работает, насколько стабильно, какие лимиты, что ломается при обновлениях — **прежде чем** просить Автора выбирать риск.

### 1.2 Не-цели
- Не строится AI-Colab 2, не выбирается стек, не пишется production-код Adapter/Courier/Secretary.
- Не проверяется масштабируемость, юридическая сторона (Spike §6), интеграция с Secretary.
- Не проверяется «разумность» ответов моделей; только механика: адрес, доставка, завершение, извлечение, восстановление.
- Не пишется браузер. Под «AI-Colab browser» понимается институциональное рабочее пространство поверх зрелого browser runtime / механизма профилей [DOC: замечание Интегратора].

### 3.3 Для WS-1 дополнительно: синтетический «провайдер» (fixture)
Локальный веб-сервис, **не имитирующий конкретного провайдера по бренду**, но воспроизводящий свойства, существенные для механики хоста: форма логина с сессионной cookie и сроком жизни; постоянный URL «беседы»; поток ответа (стриминг) и признак завершения; ленивая подгрузка длинной истории (виртуализация списка); переключаемые «обновления разметки»; искусственные отказы (сброс сессии, 429, пауза). ## 4. Ответы на обязательные вопросы (как проектные гипотезы с критериями проверки)

### 4.1 Вопрос 1. Можно ли отделить постоянное OFFICE/SEAT от браузерной сессии и конкретного OCCUPANT?

**[HYPOTHESIS]** Да — как минимум на уровне модели данных; вопрос эксперимента — не «можно ли описать», а «выдерживает ли отделение реальную замену каждого нижележащего слоя без молчаливой подмены».

Минимальная слоистая модель для эксперимента (названия условные, не схема production):
1. **SEAT/OFFICE** — стабильный идентификатор должности + ссылка на конституцию (ZOV/ZOR) + лента решений о назначениях. Не содержит URL, cookies, имён моделей.
2. **BINDING (назначение)** — запись «кто занимает кресло в такой-то период и на каком основании»; изменение — **явное событие** (succession), а не побочный эффект.
3. **OCCUPANT** — провайдер + идентификатор беседы (из URL) + наблюдаемая метка модели (если видна); может смениться, кресло остаётся.
4. **SESSION/CONTEXT** — идентификатор persistent-профиля и состояние авторизации; можно потерять (логин истёк) без потери кресла и жильца.
5. **TRANSPORT_HANDLE** — вкладка/страница/соединение; эфемерно.

**Проверки (T1.x):**
- T1.1 Перезапуск браузера: SEAT, BINDING, OCCUPANT неизменны; контекст пересоздан; handle новый.
- T1.2 Потеря авторизации (принудительное истечение cookie): SEAT/OCCUPANT сохранены, статус SEAT=`NEEDS_HUMAN_LOGIN`, а не «успех».
- T1.3 Замена жильца (новая беседа вместо старой): создаётся **явное** событие succession; прежний OCCUPANT остаётся в истории; **полномочия не наследуются автоматически** (A10) — проверка, что система не переносит «права старого жильца» новому без отдельной записи.
- T1.4 Один и тот же OCCUPANT-провайдер в двух креслах (разные беседы) — различаются и не склеиваются.
- T1.5 Одна беседа, подключённая к двум контекстам (двойное владение) — система обнаруживает конфликт, а не работает молча.
**Критерий успеха вопроса 1:** T1.1–T1.5 дают ожидаемую картину в WS-1; в WS-2 — T1.1, T1.2, T1.4 на реальных тестовых аккаунтах.
**Что не доказывается:** что модель данных — правильная онтология (решение Хранителя/Автора); доказывается только, что разделение не ломается механически.

### 4.2 Вопрос 2. Кандидаты хостинга: внешний профиль / встроенное Chromium-окружение / гибрид
Сравнение по **критериям**, без назначения победителя. Оценки — ожидания, **[HYPOTHESIS]**, подлежат проверке; в клетках нет RUNTIME-данных.

| Критерий | H-A Внешний браузерный профиль (установленный браузер, отдельный профиль на кресло, управление снаружи) | H-B Встроенное Chromium-окружение (приложение само запускает и версионирует runtime, per-seat user-data) | H-C Гибрид (видимое окно во внешнем профиле для входа/ручной работы + отдельный канал управления/наблюдения) |
|---|---|---|---|
| Сохранность логина между перезапусками | ожидается высокая (штатная работа профиля) [HYPOTHESIS] | зависит от реализации; **проверить** | как H-A для входа |
| Принятие провайдерами (SSO/антибот) | ожидается лучше: обычный пользовательский браузер | риск блокировки входа во «встроенных» окружениях (**отдельно проверить** для входа через сторонний SSO) | как H-A |
| Контроль версии runtime | слабый: автообновления браузера могут ломать управление | сильный: версию можно закрепить | смешанный |
| Скорость старения runtime относительно требований провайдеров | обновляется браузером сам | стареет, если приложение не обновляется; провайдер может отказать «старому браузеру» [HYPOTHESIS] | смешанная |
| Видимый ручной fallback | естественный: это обычное окно | нужно проектировать | естественный по построению |
| Площадь атаки управляющего канала | отладочный порт/расширение = полный контроль над авторизованным браузером | то же, но порт можно держать внутри процесса | порт всё ещё нужен, если есть автоматизация |
| Изоляция профилей друг от друга | зависит от дисциплины (блокировка профиля, одновременный запуск) | управляется приложением | как H-A |
| Единое окно рабочего пространства | нет (несколько окон) | да | нет/частично |
| Нагрузка на сопровождение | обновления браузера и провайдеров | + сопровождение собственного runtime | обе |
| Зависимость от внешней программы | да | нет (но от встроенной) | да |
| Оценка «чтение без отправки» | возможна | возможна | возможна |

Что **измеряет** WS-1/WS-2 для каждого кандидата (если Автор разрешит сравнение нескольких): доля восстановленных входов; время восстановления; число потерянных логинов за серию перезапусков; ручные вмешательства; обрывы управляющего канала; поведение при обновлении runtime; конфликт при двойном запуске профиля.
**Дополнительный вариант вне списка Автора:** управление изнутри страницы (расширение). Не включаю в план без решения; упоминаю как открытую ось, чтобы её закрытие было осознанным.

### 4.3 Вопрос 3. Минимальные наблюдения для проверки восстановления после рестарта

**Снимок «до» (pre-image), на каждое кресло:**
- `seat_id`, `binding_id`, `profile_id` (идентификаторы, не пути с секретами);
- провайдер; **идентификатор беседы** (из URL; сам URL фиксировать без токенов в query);
- заголовок страницы/беседы (если виден) — как слабый признак;
- число сообщений по ролям (user/assistant) в загруженном виде **и** отметка «история полностью подгружена / нет»;
- **отпечаток** (SHA-256) последних N сообщений и длина каждого — без хранения текста там, где текст не нужен;
- состояние генерации: idle / generating / unknown;
- `send_nonce` последнего отправленного сообщения (если было) и локальный статус отправки;
- время (UTC) и номер эпохи (`restart_epoch`);
- состояние авторизации (авторизован / требует входа / вызов: CAPTCHA/2FA/ошибка).

**Событие:** принудительный перезапуск (штатное закрытие; kill процесса; потеря сети; перезагрузка среды) — **разные виды рестарта различаются в отчёте**.

**Снимок «после» (post-image):** то же, плюс:
- разрешился ли адрес в ту же беседу (id совпал);
- совпали ли число и отпечатки сообщений «до»; появились ли **новые** сообщения (дельта) — в т. ч. ответ, завершившийся во время простоя;
- найден ли `send_nonce` в беседе (для решения «доставлено / не доставлено»);
- состояние генерации;
- что потребовало человека.

**Вердикты восстановления (закрытый список):**
`RECOVERED` (идентично) · `RECOVERED_WITH_DELTA` (то же + объяснимое новое) · `AMBIGUOUS` (нельзя однозначно сказать о доставке/полноте — **не** округляется до успеха) · `NEEDS_HUMAN` (логин/CAPTCHA/2FA/конфликт) · `LOST` (беседа недоступна/иная) · `MISMATCH` (другая беседа с тем же адресом/заголовком — тревога). Тихое «успешно» при расхождении — провал сценария.
**Минимальность:** без идентификатора беседы + счётчиков + отпечатков + nonce нельзя отличить RECOVERED от MISMATCH и AMBIGUOUS; остальное — наблюдения, не критерии.

### 4.4 Вопрос 4. Можно ли сохранить функциональность рабочего пространства без автоматической отправки сообщений?
**[HYPOTHESIS]** Да. Режимы (каждый — отдельный уровень разрешения):
- **M0 View-only.** Рабочее пространство открывает persistent-контексты кресел, показывает реестр, статусы, ленту событий; **не посылает ввод в страницу и не читает BODY** (только метаданные окна/состояние входа).
- **M1 Observe/Extract.** Чтение уже существующих сообщений и сохранение (технический доступ к BODY, отдельное разрешение, §4.6). Без ввода.
- **M2 Assisted manual.** Система готовит пакет (envelope + BODY) для человека: экспорт в файл/буфер; человек вставляет и нажимает «отправить» сам; затем импорт ответа человеком или M1-извлечение. **Нажатие «отправить» только человеком.**
- **M3 Compose-draft (спорный).** Система вписывает текст в поле ввода, не отправляя. Это уже запись в DOM чужого UI: отдельный риск (случайная отправка клавишей, перезапись черновика) — **включать только отдельным решением**.
- **M4 Auto-send** — только WS-3, отдельное разрешение.

**Проверка (T4.x):** в WS-1/WS-2 открыть N кресел в M0 на ≥ 24 ч (WS-2: ≥ 24 ч, WS-1: имитация), пережить рестарты, и убедиться, что (a) исходящих сообщений **0** (подтверждается по журналу сети провайдера/fixture и по счётчикам бесед), (b) реестр и статусы корректны, (c) переход M0→M2 возможен без сброса. Успех: полезная часть (адресация, статус, восстановление, видимость) работает без единой отправки.
**Что не доказывается:** что без автоотправки достигается A1 («Автор не шина»); M2 ручная.

### 4.5 Вопрос 5. Как обеспечить видимый ручной fallback
Дизайн-требования, превращаемые в проверки:
- F1. Каждое кресло — реальное видимое окно/вкладка, в которую человек может писать напрямую (механизм зависит от хоста; проверить для H-A/H-B/H-C).
- F2. Постоянный индикатор режима кресла: `AUTOMATION OFF / PAUSED / ACTIVE` и последнего статуса (RECOVERED/AMBIGUOUS/…) — виден без открытия логов.
- F3. Аварийное отключение автоматизации одним действием, действующее немедленно, **включая** запланированные отправки; повторное включение — явное.
- F4. Любое действие автоматики записывается в журнал до выполнения («намерение») и после («результат»); при расхождении — AMBIGUOUS.
- F5. При неопределённости **никаких молчаливых повторов отправки** (A7); статус `NEEDS_HUMAN` с инструкцией, что проверить глазами.
- F6. Ручной обход: экспорт пакета и импорт ответа (M2) работают при полностью выключенной автоматике.
- F7. Система распознаёт **человеческое** вмешательство (сообщение, отправленное вручную) и не затирает его своей моделью состояния — пересинхронизирует.
**Проверки (T5.x) — инъекция отказов:** (1) отключить автоматику в середине сценария — человек завершает шаг; (2) оборвать управляющий канал сразу после отправки (= Spike B1) — система показывает AMBIGUOUS и подсказку, а не «успех»; (3) принудительный logout — NEEDS_HUMAN; (4) человек отправил сообщение сам во время «паузы» — F7.
**Успех:** во всех инъекциях видимый статус корректен, молчаливых успехов/повторов 0.

### 4.6 Вопрос 6. Технический доступ к сообщению vs право читать его по смыслу
Определения уровней (для эксперимента, не как архитектура):
- **L0 Metadata:** seat/binding, тип события, время, размеры, хэши, статусы, счётчики. Видна «смысловому» участнику.
- **L1 BODY-transport:** технический доступ к байтам тела (вставить / извлечь / посчитать длину и хэш). Не интерпретирует.
- **L2 Semantic:** чтение содержания по смыслу. Только участник, чей ZOV это допускает.

Принцип проверки: **утечки через побочные каналы**. Технический доступ к BODY неизбежно оставляет следы: журналы, скриншоты, видеотрассы и DOM-снимки при отладке (Spike §4 прямо упоминает «скриншоты DOM»), HAR/сетевые трассы, crash-дампы, буфер обмена, история браузера, автосохранение профиля. Каждый — потенциальный канал L1→L2.
**Проверки (T6.x), в DTE с синтетическими данными и canary:**
- T6.1 Тестовые BODY — синтетические и несмысловые (nonce + заполнитель), чтобы проверка изоляции **сама** не требовала семантического чтения; плюс canary-строки.
- T6.2 Журнал и хранилище метаданных не содержат BODY и canary (поиск по файловой системе, включая каталоги профилей и временные).
- T6.3 Артефакты отладки (скриншоты/трассы/HAR) либо отключены в боевом режиме, либо хранятся в зоне L1 с отдельными правами; проверить, что процесс «семантического» принципала не имеет к ним доступа (ОС-права, не соглашение).
- T6.4 Два принципала (разные пользователи ОС или контейнеры): «L0-читатель» не может открыть BODY-хранилище; «L1-обработчик» не пишет BODY в L0-хранилище. Попытка нарушения даёт отказ ОС, а не «договорённость».
- T6.5 Ошибки и исключения не вытаскивают BODY в сообщение об ошибке.
**Привязка к ступеням (D7):** WS-1 — T6.1, T6.2, T6.5 и проверка конфигурации T6.3 (отладочные артефакты отключены или лежат в L1-зоне); WS-2/WS-3 — полностью T6.3 и T6.4 (два принципала, права ОС), так как там появляются реальные профили и реальные BODY.
**Уровень свидетельства:** это B-lite — проверка самого эксперимента на отсутствие утечки. Полная изоляционная верификация Roadmap Gate B (для будущей системы) — отдельный эксперимент, этим планом не заменяется.
**Что не доказывается:** что полный Adapter будет «слепым» (в плане нет Adapter); доказывается лишь, что хост и инструментарий не нарушают разделение по умолчанию.

### 4.8 Вопрос 8. Какие проверки — только в специально выделенном тестовом окружении
Только в DTE (§3.2) и только после отдельного разрешения:
1. Любой вход в аккаунт провайдера (даже тестовый) и хранение его профиля.
2. Любая отправка сообщения в чат провайдера (WS-3, и M3).
3. Подключение к браузеру по отладочному каналу (CDP-attach и аналоги), запуск расширений.
4. Любые вызовы внутренних API провайдера с cookies сессии (A-API, пред-проверка наличия status-признака).
5. Принудительные рестарты, kill процесса, отключение сети, истечение сессии.
6. Сценарии B/B1 (обрыв сразу после Enter).
7. Проверка антибота/рейт-лимитов (наблюдательно, не провоцировать).
8. Проверка изоляции с canary-секретами и двумя принципалами.
9. Длительные наблюдения (Stage 2, 2 недели), ежедневные запуски.
10. Сравнение хостов с реальными профилями.
**Допустимо вне DTE (на бумаге/без сети):** WS-0; разработка схемы наблюдений; обзор документации; анализ уже сохранённых текстов.
**Никогда (в рамках этого плана, ни в какой среде):** живые чаты Коллаборации; обход CAPTCHA/2FA; использование основных аккаунтов; хранение секретов в пакетах между ролями.

### WS-1. Механика хоста на синтетическом провайдере
- Среда: DTE + fixture (§3.3). Живых сервисов нет, аккаунтов нет.
- Проверяет: T1.x, T4.x(M0/M2), T5.x, T6.x, часть R-4/R-5/R-7 в синтетическом виде, сравнение H-A/H-B/H-C по §4.2 (если разрешено >1 хоста).
- Серия (пилот WS-1a): N=10 перезапусков на хост × 4 вида рестарта (штатный/kill/сеть/перезагрузка среды) × 2 кресла = 80 прогонов на хост; отдельный короткий прогон на ≥3 одновременных кресла (конкуренция). Расширение до N=30 (WS-1b) — только по результатам пилота и по решению Интегратора/Автора; бюджет времени и износ профилей (lock-файлы после kill) записываются, профиль между сериями пересоздаётся или проверяется. Пороговых критериев по доле успеха в WS-1 нет — это измерения. Для WS-1 дополнительно: fixture отдаёт «старый User-Agent» и проверяется реакция хоста.
- N=30 по Spike v3.1 относится **только к WS-3** и не меняется.
- Выход: таблица «хост × критерий» с измерениями; **не** рекомендация.

### WS-2. Живые тестовые аккаунты, только чтение, без отправки
- Предусловия: P-A…P-C; WS-1 завершён с приемлемым результатом **или** осознанное решение Автора пропустить.
- Подготовка (человек): создать тестовый чат с искусственной историей (Spike Этап 0, вариант А); войти вручную.
- Проверяет: T1.1/T1.2/T1.4 в реальных интерфейсах; восстановление RECOVERED/…; M0 ≥ 24 ч; M1 извлечение существующих сообщений **двумя путями** (DOM и внутренний API) с протоколом: что работает, стабильность, лимиты, что ломается; вход после истечения сессии (NEEDS_HUMAN).
- Выход: данные по каждому провайдеру отдельно (матрица провайдер × путь × наблюдения), включая случаи «недоступно/блок».
- Остановка: любое предупреждение/блокировка аккаунта = STOP (§6.3).

### WS-3. Продолжение Endpoint Spike v3.1 (отправка и т. д.)
Выполняется **строго по документу Endpoint_Spike.md v3.1** (SHA-256 4a9256d5…), без изменения критериев в ходе серии. Мои дополнения — только наблюдения, не критерии:
- Этап 0: проверка official-but-limited API-путей; 5/5 последовательных вызовов без создания новой сессии; вариант выбора чата (А/Б) фиксируется до начала. **Я рекомендую вариант А** (служебный чат); вариант Б — риск Автора [NEEDS_AUTHOR].
- Этап 1: сценарии A-DOM, A-API, A-long, B, B1, C; N=30; пороги 27/30 (90%): A-DOM, A-API, C; 24/30 (80%): A-long, B, B1. Раздельно: timeout vs premature vs truncation.
- Этап 2: ежедневный запуск A две недели; фиксируются изменения DOM, обрывы, CAPTCHA/блокировки; ось «стоимость поддержки» заполняется только здесь.
- Инструментарий харнесса: спайк называет Playwright + CDP-attach как «выбор для тестового харнесса, не обязательство» [DOC]. Данный план сохраняет это допущение **только** как харнесс; **вторая независимая реализация драйвера** — желательна, чтобы результат не оказался свойством одного инструмента [PROPOSAL].
- Дополнения к наблюдениям (мои): `send_nonce` в каждом пинге и проверка по нему (для B1 и AMBIGUOUS); отдельное поле «имя пути» (DOM/API); отметка «человек вмешивался» (Y/N) на каждый запуск; версия runtime и дата на каждый запуск; проверка, что извлечён «только новый ответ» (по отпечаткам «до» и «после»).
- Что WS-3 **не** решает: выбор DOM/API для production; допустимость по условиям провайдеров; масштаб.

## 6. Критерии успеха и провала

### 6.1 Критерии по ступеням
| Ступень | Успех (необходимое условие для запроса следующей ступени) | Провал / тревога |
|---|---|---|
| WS-0 | Схема наблюдений и сценарии приняты ревьюерами без критических замечаний | Нельзя однозначно определить вердикт RECOVERED/AMBIGUOUS по наблюдаемым данным → доработать схему |
| WS-1 | Для оцениваемого хоста: T1.1–T1.5 выполняются; **0 молчаливых MISMATCH/«успехов при расхождении»**; M0 без исходящих; все инъекции T5 показывают корректный статус; T6.2–T6.5 без утечек | ≥1 молчаливая подмена беседы; ≥1 случай, когда fallback не виден; любая утечка BODY/canary |
| WS-2 | Вердикты согласованы с реальностью в ≥ 90 % рестартов на провайдер×хост. Проверка: автоматический оракул по заранее известной «затравке» тестового чата (счётчики, отпечатки) + человеческая проверка **всех** AMBIGUOUS / NEEDS_HUMAN / MISMATCH / LOST и случайной выборки не менее 20 % RECOVERED; 90 % — оценка по выборке, с указанием размера выборки; остальные — честно AMBIGUOUS/NEEDS_HUMAN; 0 исходящих сообщений | Любой MISMATCH без обнаружения; предупреждение/блок аккаунта (STOP); провайдер недоступен для чтения обоими путями → фиксируется как факт |
| WS-3 | Пороги Spike v3.1 (см. выше) **и** 0 случаев «premature completion без обнаружения» среди принятых успехов | Любой порог не достигнут → процедура Spike §5; premature > 0 среди «успехов» → вывод аннулируется для данной платформы |

### 6.2 Общие STOP-условия (останавливают всё, возвращают Интегратору)
- Предупреждение/ограничение/блокировка аккаунта, запрос подтверждения личности вне рамок, подозрение на компрометацию профиля.
- Любой признак доступа к живым чатам Коллаборации или основным аккаунтам.
- Обнаружение BODY/canary там, где их быть не должно.
- Любая отправка при режиме M0/M1.
- Желание «починить», чтобы пройти критерий (изменение критерия посреди серии запрещено).
- Невозможность однозначно сопоставить запуск с версией окружения.

### 6.3 Что считается результатом, а что — нет
Результат — **измерение с паспортом**, а не рекомендация. Отрицательный результат («примитив недостаточно устойчив для платформы X на основе текущих данных» — формулировка Spike §5) — полноценный результат. «Не удалось проверить» ≠ «провал» и фиксируется отдельно.

### 6.4 Исключено принципиально
Обход CAPTCHA/2FA/антибота; подделка клиента для обмана провайдера; массовые запросы для выяснения лимитов; использование украденных/общих учётных данных.

## 9. Фиксация ревизии HF-снапшота: блокер и проверяемые способы
**Блокер.** Из этой среды доступны: `hf_fs` (не возвращает commit/sha; не читает файлы с NUL-байтами), `hub_repo_details` (дата «Updated 16 Apr 2026»), WebFetch к huggingface.co (требует подтверждения пользователя; ответ — резюме, не байты). Шелл huggingface.co не достаёт (прокси 403; не обходится). Поэтому **точный commit SHA датасета `lhc-lab/AI-Colab` мной получить нельзя без доп. действия**.
**Проверяемые способы (в порядке предпочтения):**
1. **Commit SHA через API.** Любой участник с доступом к HF выполняет `GET https://huggingface.co/api/datasets/lhc-lab/AI-Colab` и сообщает поле `sha` и `lastModified`, либо `git ls-remote https://huggingface.co/datasets/lhc-lab/AI-Colab`. Проверка независима: любой второй участник повторяет и сверяет.
2. **Если пользователь подтвердит WebFetch для двух URL** (`…/api/datasets/lhc-lab/AI-Colab`, `…/resolve/main/requirements.txt`), я получу поле `sha`, но ответ будет резюме модели; дополнительно проверить способом 1.
3. **Манифест содержимого вместо (или вместе с) ревизии.** Построить список `путь, размер, SHA-256` по **фактической локальной копии E:** (делает Samurai по разрешённой задаче) и сравнить с паспортами P0-пакетов; общий «корневой» хэш = SHA-256 отсортированного манифеста. Это фиксирует то, что реально будет запускаться, и ловит расхождение HF ↔ E:.
4. **Парный паспорт:** `HF_COMMIT_SHA` (способ 1) + `MANIFEST_SHA256` (способ 3). Запуск смоук-плана допускается только при совпадении паспортов P0 с манифестом; расхождения фиксируются как отдельные находки.
**Рекомендация (PROPOSAL):** считать закрытым только пару «commit SHA + manifest». До этого статус остаётся `REVISION HF: UNKNOWN`, и он блокирует ИСПОЛНЯЕМЫЙ смоук-тест легаси; на WS-0…WS-3 не влияет.
`requirements.txt` — отдельный пункт: нужны **сырые байты** (способы: манифест из E: + hex-превью, либо WebFetch raw-URL с подтверждением). Читать его Автору вручную не требуется.
