## 1. Главный вопрос ревью: не наследует ли проект легаси-архитектуру незаметно?
Вывод: **по замыслу — нет; по формулировкам есть четыре места, где дрейф возможен.** Все — управляемые.

**1.1 «Сделать так, чтобы запустилось» превращается в ремонт.** Если при сбое запуска допускается «поправить импорт/путь/версию, чтобы пройти дальше», результат — уже не легаси, а наш патч, но отчёт назовёт его RUNTIME_OK. Это самый тихий путь реконструкции.
[PROPOSAL] `RUNTIME_OK` присваивать **только** при запуске **без единой правки кода и конфигурации сверх DUMMY-переменных**, с записью точного условия запуска (SHA манифеста, версии интерпретатора и пакетов, команда, окружение). Любая правка → отдельный статус `RUNTIME_OK_AFTER_MODIFICATION` с diff; в карту совместимости он не переносится как «работающее легаси».
Аргумент: F-1, F-3, F-15, F-20 предсказывают падения; ремонт каждого — это решение дизайна, а не наблюдение.

**1.2 Критерий «зелёного» как неявный выбор.** Если заранее перечислены точки входа и «что должно ответить», структура теста подсказывает, что считать нормой — и закрепляет конструкцию (Quart-маршруты, `/api/secretary`) как эталон.
[PROPOSAL] В отчёт — таблица «факт ↔ ожидание», где ожидание берётся из документов с меткой [DOC], а не из текущей структуры; и отдельная строка «что НЕ проверялось и почему».

**1.3 Порядок точек входа.** Запуск `start_server.py` первым, так как это «официальный» лаунчер, закрепляет его как «живой вход».
[PROPOSAL] Вход — результат эксперимента, не гипотеза: запускать все перечисленные в **случайном или нейтральном (алфавитном) порядке**, независимо; фиксировать, какие стартуют сами по себе. Ответ Автора допустим как `[RECALL: Author]` и сверяется (это согласуется с правками v1.2).

**1.4 Смысловая преемственность идёт из документов, не из «работающего кода».** Если часть запустилась, возникает соблазн считать её кандидатом на reuse. Roadmap/Readme прямо различают «что осталось работоспособным» и «что мы хотим иметь». [PROPOSAL] В шаблоне отчёта явно записать: `RUNTIME_OK` не равно `REUSE_CANDIDATE`; переход возможен только через отдельное решение триады.

## 2. Безопасность запуска (по прочитанному коду)
Это не возражения против эксперимента, а условия, без которых отчёт RUNTIME_OK/FAILED недостоверен или эксперимент опасен.

2.1 **`start_server.py` — действие над хостом [CODE: F-16].** В `__main__` вызываются `clean_python_cache()`, `ensure_port_free(5000)` (завершает процессы на порту 5000) и `os.system(...)` для запуска uvicorn с `--workers 2 --reload`. Порт 5000 захардкожен — ваш loopback :5999 для этого файла **не действует**. Если запускать как есть, он (а) удаляет кэши в каталоге запуска и (б) может завершить посторонний процесс на :5000 на машине исполнения.
[PROPOSAL] Либо не запускать `start_server.py` как скрипт, а проверять его статически/через импорт функций без вызова `__main__`; либо запускать только в контейнере/ВМ с отдельным сетевым пространством, где на :5000 нет ничего, и cwd = `smoke/`. Решение — по разрешению Автора, обозначить как риск R-новый.

2.2 **`app.py` — `app.run(debug=True, host='0.0.0.0', port=5000)` [CODE: F-11].** Не запускать через `python app.py`; использовать только заданный вами loopback-запуск ASGI-сервером с `host=127.0.0.1`. Режим `debug=True` отключён при запуске через uvicorn — зафиксировать, что отчёт описывает именно такое условие.

2.3 **Побочные эффекты при импорте [CODE: F-22, app.py L18/L37/L138].** `shared_state` создаёт файл в cwd при импорте; `load_dotenv()` читает `.env` из окружения/каталога; `from scripts.openrouter_models_updater import update_models` в `app.py` импортируется на уровне модуля (фоновый вызов закомментирован, но модуль импортируется — его собственные импорты и побочные эффекты не прочитаны [UNKNOWN]). В `smoke/` не должно быть реального `.env`/конфигов с секретами — DUMMY только (в плане это есть; прошу перечислить явно также `config/gemini_sockets.json` с путём бинарника).

2.4 **Executor и stub-бинарник [CODE: gemini_cli_executor.py L21–38].** Бинарник ищется: `gemini_cli_path` из конфига → `shutil.which("gemini")` → `integrations/gemini_cli.py`; иначе `RuntimeError`. Чтобы stub не подменялся реальным `gemini` на машине, PATH в `smoke/` должен содержать **только** каталог со stub; `gemini_cli_path` — путь внутри `smoke/`. Executor передаёт `env=os.environ` и (на DEBUG) логирует первые 5 символов `GEMINI_API_KEY` [F-13] — окружение запуска должно быть очищено (`env -i`), DUMMY-ключ не должен быть похож на реальный.

2.5 **GCB [CODE: F-7].** `GCBEngine()` создаётся при старте всех четырёх приложений; движок исполняет `create_subprocess_shell` из JSON-очереди. Условие: очередь в `smoke/` пуста/отсутствует, фоновую задачу не стимулировать; `shell`-ветку **не вызывать**, даже со stub-командой (хотя бы потому, что `shell` исполняет строку с правами пользователя). Проверку GCB вести только статически (уже сделано) либо в отдельной ВМ без прав.

2.6 **`role='../evil'` [CODE: F-23].** Проба верна, но безопасна только если `base_dir` ChatStorage находится глубоко внутри `smoke/` и целевой путь вне него проверяется **до** записи (или каталог-приёмник за пределами `smoke/` — песочница). Иначе проверка превращается в реальную запись вне рабочего каталога. Рекомендация: базовый каталог = `smoke/chats`, а «жертвенный» каталог для выхода — заведомо созданный `smoke/_sink/` и проверка факта записи **только** в нём; в остальном — только вызов санитайзера/построения пути без записи.

2.7 **Платформа исполнения [UNKNOWN].** Пути D:/E: в легаси и msvcrt-ветка `shared_state` указывают на Windows; «свой venv, loopback 5999» подразумевает какую-то ОС. Нужно зафиксировать ОС/версию Python исполнителя: результат на Linux не равен результату на Windows (блокировки `msvcrt` против `fcntl`, пути, `create_subprocess_shell`). Статус `RUNTIME_OK` должен быть привязан к ОС.

## 3. Позиции по темам, связанным с §12 (ответы на 12.1–12.4 — после получения формулировок)
- **Какой файл считать «живой» точкой входа:** не решать заранее; результат эксперимента (см. 1.3) + возможная пометка `[RECALL: Author]`. [DOC] называет `app2.py`; лаунчер указывает на `app.py`; `app3.py` по статике не стартует. Три источника расходятся — это и есть содержание теста.
- **Что считать успехом запуска:** старт процесса ≠ работоспособность. Минимальные уровни: `IMPORTS_OK` → `APP_STARTS` → `ROUTE_RESPONDS` (без внешней сети, с DUMMY) → `FLOW_COMPLETES` (один круг роли через stub). Отчёт указывает **достигнутый уровень**, а не одно слово.
- **Что делать при расхождении запуска и статического анализа:** фиксировать `[CODE×RUNTIME]` как отдельный класс находок; не переписывать F-номера задним числом, добавлять новый номер; повышение уровня (STATIC → RUNTIME_VERIFIED) — только для фактически запущенного.
- **Граница с Web-Seat планом:** Gate B Roadmap (изоляция metadata/BODY) и Spike v3.1 к легаси не относятся и в смоук-тест не входят. Смоук-тест отвечает только на вопрос «что из старого AI-Colab работает» (пункт 1 «первой серии» по Readme).
