## A. Кодирование снимка для сборки (интерпретации v0.4; прошу сверить)
v0.4 §3 перечисляет поля, но не их кодирование. Для сборки принимается следующее. Каждый пункт — моя интерпретация, помечен как кандидат на включение в контракт v0.3.
- **I-1 Беседа не открылась.** В `post` есть булево поле `conversation_opened`. Если `false`, поля содержимого (`conv_id`, `chain`, `tail_fps`, `n_msgs`, `extraction_path`, `fp_version`, `history_complete`) могут быть `null` и не считаются «обязательными» для правила 1. Иначе V3, V4, V7 нельзя вычислить. В `pre` оно всегда `true`.
- **I-2 Цепочка списком.** `chain` — список накопленных хэшей `H₁…Hₙ` (по одному на сообщение), текст не содержит. Проверка префикса: `post.chain[n_pre-1] == pre.chain[n_pre-1]`, где `n_pre = len(pre.chain)`. Если `len(post.chain) < n_pre`, правило 7 срабатывает (`PREFIX_CHANGED`).
- **I-3 Правило 7a.** Применяется, как в v0.4, только при `n_post == n_pre`: `tail_fps` (список `{idx, role, len, msg_fp}`) сравнивается поэлементно по `idx`. Замечание DeepSeek: при `n_post ≠ n_pre` правило не применяется, идёт правило 9. Открытый вопрос: расхождение в `tail_fps` внутри префикса при `n_post > n_pre` остаётся незамеченным; для среза принимаем как известное ограничение.
- **I-4 Формула отпечатков.** v0.4 §3 пишет `Hᵢ=SHA256(Hᵢ₋₁ ‖ role ‖ SHA256(norm(text)ᵢ))` схематически. Точное кодирование для `fp_version=1` задаёт `BUILD_001_FP_GOLDEN_VECTORS.json` (`msg_fp = SHA256(role ‖ U+001F ‖ text_hash)`, затем цепочка по `msg_fp`). Это уточнение, а не повторение формулы v0.4; статус эталона `UNVERIFIED`. Для STEP 2–3 отпечатки не вычисляются — движок получает готовые хэши.
- **I-5 Атрибуция дельты.** В `post` список `attributions` из `{idx, by, ref}`: `by=send_nonce` (требует `send_status=CONFIRMED_PRESENT` и `ref == send_nonce`) или `by=operator_action` (требует записи с таким `action_id` в `operator_actions`). Дельта атрибутирована, если для каждого `idx` из `[n_pre, n_post)` есть корректная запись.
- **I-6 Флаги наблюдения.** Двойное владение и запрет автоматизации передаются в `post.flags` значениями `double_ownership` и `automation_forbids_observation`. Прочие флаги (`model_label_changed`, `ui_variant_changed`) проходят в вердикт как есть.
- **I-7 Инвалидность (правило 1).** Снимок невалиден по перечню v0.4 §2.1 п.1; дополнительно здесь определено: значение вне закрытых списков (§1.1: состояния SESSION/TRANSPORT/OCCUPANT, `generation_state`, `extraction_path` ∈ {DOM, API, MANUAL}, `send_status`, `restart_kind`); поле `send_attempt_logged=true` при `send_status=NONE`; метки времени не в формате `YYYY-MM-DDTHH:MM:SSZ`.

## STEP 2 — движок вердиктов (чистая функция, без браузера)

**Цель.** Реализовать `verdict(pre, post)` по правилам v0.4 §2.1 и доказать его на бумажных векторах.

**Вход.** `pre`, `post` — снимки по кодированию §A; допускается `pre = null`.
**Выход (структура).** `verdict` ∈ {RECOVERED, AMBIGUOUS, LOST, NEEDS_HUMAN, MISMATCH}; `reason` (код или null); `delta` (bool или null); `send_status` (из post, если есть); `flags`; `decisive_rule` (напр. `"7a"`); `rules_trace` (правила, проверенные по порядку до решающего); `pre_ref`/`post_ref` (`snapshot_id`). Правила применяются в порядке 1, 2, 3, 4, 5, 6, 7, 7a, 8, 9, 10; первое сработавшее побеждает.

**Охрана L0 (отдельно от вердикта).** Если в снимке встречается ключ из списка `text`, `content`, `body`, `messages`, `prompt`, `completion` (на любом уровне вложенности), функция не выдаёт вердикт, а возвращает ошибку `L0_VIOLATION` с путём ключа; это регистрируется как ошибка, не как вердикт. Это интерпретация границы L0/L1 (§6 контракта 001).

**Критерии PASS.**
1. V1–V18 из `BUILD_001_STEP2_VECTORS.json`: все совпадают по `verdict`, `reason`, `delta`, `decisive_rule`, `send_status`, `flags`.
2. E1–E14 (дополнительные случаи, не из v0.4): совпадение, либо расхождения перечислены в отчёте как расхождения. Векторы автором не исполнялись; ожидаемое может быть неверным, и решать это будем мы с DeepSeek-developer, а не исполнитель молча.
3. Чистота: нет I/O, часов, случайных чисел, сети, глобального состояния. Двойной вызов на одном входе даёт одинаковый вывод; входные объекты не изменяются (глубокое сравнение до/после).
4. Вердикт всегда один из пяти; для каждого случая `rules_trace` оканчивается на `decisive_rule`.
5. Порядок: случаи E8–E12 проходят (правило 2 раньше 4, 4 раньше 5, 5 раньше 6, 6 раньше 7, 7 раньше 8).
6. Тест запуска печатает по строке на случай (`V1 PASS` / `V5 FAIL got=… expected=…`) и итог `STEP2 PASS 32/32` либо `STEP2 FAIL k/32`; код выхода ненулевой при FAIL.

**Запрещено.** Править векторы, чтобы получить PASS; чтение файлов, кроме файла векторов; проверка отпечатков в этом шаге (это STEP 4/5); оставлять вердикт «по умолчанию» при неожиданном входе (неожиданный вход = правило 1, а не исключение, кроме L0_VIOLATION).

**Отчёт.** Файлы, команда, полный вывод теста, список расхождений, список неясностей в §A.

## STEP 3 — реестр кресел и журнал ошибок

**Цель.** Постоянное хранилище, переживающее смерть любого процесса, с явными событиями и неудаляемыми журналами. Реализует §1–§3 и §7 контракта 001.

**Хранимое (минимум).**
- Кресла: `seat_id`, `seat_state` (VACANT/BOUND/SUSPENDED/RETIRED).
- Привязки: `binding_id`, `authority_epoch`, режим `M0…M4`, индикатор `AUTOMATION` (OFF/PAUSED/ACTIVE), основание предоставления (`granted_by`, `reason`, `ts_utc`).
- Жилец: `provider`, `conv_id`, `occupant_state`; сессия: `profile_id`, `session_state`; транспорт: `handle_id`, `transport_state` (эфемерный, хранится как последнее наблюдение).
- Журнал событий (append-only): каждое изменение чего-либо — запись `{event_id, ts_utc, actor, kind, seat_id, before, after, reason}`.
- Снимки (только L0), вердикты (с `rules_trace`, ссылками на снимки), разрешения (`resolution`: `resolved_by`, `resolved_at`, основание) — отдельными записями; вердикт не переписывается (v0.4 §2.3).
- `operator_actions`: `{action_id, kind, ts_utc, operator, seat_id, note}`.
- Реестр ошибок (append-only): `{err_id, ts_utc, seat_id|null, op, class, code, expected, observed, evidence_refs}`.

**Операции** (названия условные, форма — на усмотрение): зарегистрировать кресло; создать привязку с записью о предоставлении; подтвердить жильца (через действие оператора); применить наблюдение (смена состояний слоёв); succession (новая привязка, новое `authority_epoch`, прежний жилец `REPLACED`); записать снимок; записать вердикт; записать разрешение (только действием человека); записать действие оператора; записать ошибку; экспорт статуса.

**Экспорт статуса** (источник панели §7 контракта 001): по каждому креслу `seat_id`, `seat_state`, `occupant_state`, `session_state`, `transport_state`, режим `M*`, `AUTOMATION`, последний вердикт с причиной и `send_status`.

**Критерии PASS** (каждый — отдельный тест с печатью `T3-n PASS/FAIL`; итог `STEP3 PASS k/k`).
- **T3-1** Постоянство: записать состояние в процессе A, завершить процесс принудительно, прочитать в процессе B — состояния идентичны.
- **T3-2** Идентичность: два кресла с одинаковым провайдером и адресом получают разные `seat_id`; повторная регистрация с теми же атрибутами даёт новый id; `seat_id` не содержит подстрок провайдера, адреса, `conv_id`, `profile_id`.
- **T3-3** Двойное владение: привязка второго кресла к уже занятой паре `(provider, conv_id)` отклоняется; ошибка в реестре.
- **T3-4** Succession: смена жильца возможна только событием с записью предоставления и ростом `authority_epoch`; без записи — отказ + ошибка; повторное открытие хранилища не меняет привязку и эпоху (SS-1, SS-8).
- **T3-5** События: воспроизведение журнала событий с нуля даёт состояние, побайтно равное текущему. Состояние, изменённое без события, невозможно.
- **T3-6** Неизменяемость: после записи разрешения исходный вердикт не изменён; журналы только растут (хэш префикса прежнего файла не меняется); API изменения и удаления записей журналов отсутствует.
- **T3-7** Нет автоповышения: запись разрешения с актором `system` отклоняется; принимается только оператор с основанием (SS-5).
- **T3-8** Режим после рестарта: операция «рестарт» переводит режим в `M0` и `AUTOMATION` в `OFF`/`PAUSED`; повышение возможно только записью `operator_actions` (И-5 контракта 001).
- **T3-9** L0-охрана: запись, содержащая запрещённые ключи (`text`, `content`, `body`, `messages`, …) или строку длиннее заданного порога в поле, не предназначенном для строк такой длины, отклоняется; в тесте запись с синтетическим маркером `CANARY-…` отклонена, и маркер не найден ни в одном файле хранилища и журналов.
- **T3-10** Реестр ошибок: каждый отказ из T3-3, T3-4, T3-7, T3-9 порождает запись с полным набором полей; записи не удаляются и не правятся.
- **T3-11** Устойчивость к прерыванию: цикл записей, принудительное завершение процесса не менее 50 раз в случайные моменты; после каждого завершения хранилище читается, состояние равно некоторому префиксу журнала событий (нет битых записей и частичных состояний).
- **T3-12** Вердикт из STEP 2: вердикт для вектора V1 и V5 записывается со ссылками на снимки и `rules_trace`; чтение возвращает те же поля.
- **T3-13** Экспорт статуса: для двух кресел выдаёт все поля §7; значения соответствуют событиям.
- **T3-14** Второй писатель: одновременная запись из двух процессов либо сериализуется без потерь, либо второй получает определённый отказ с записью в реестр ошибок; тихой потери данных нет.

**Запрещено.** Хранить тексты сообщений; выводить `seat_id` из атрибутов; API изменения/удаления журналов; автоматические повторы записи без записи в журнал; сеть, браузер, старый код; менять STEP 2.

**Отчёт.** Файлы, команды, вывод тестов дословно, описание выбранного формата хранения (одной строкой), результат T3-11 (число прерываний и исход), расхождения со SPEC.
