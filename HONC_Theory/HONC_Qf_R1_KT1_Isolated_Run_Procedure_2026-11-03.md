## 1. Устройство

**Папка прогона** — `/var/tmp/kt1-runs/<метка>-<время UTC>/`, владелец root, права 0711: nobody может пройти, но не читать список. Папки сессии закрыты 0700 для root, поэтому прогоны лежат вне их.

| Папка | Хозяин, права | В песочнице | Назначение |
|---|---|---|---|
| `src/` | root, 0444 / 0555 | `/sandbox/src`, только чтение, текущая папка | распакованный архив скрипта |
| `work/` | **tmpfs с квотой** (по умолчанию 512 МиБ и 20 000 файлов), nobody, 0700 | `/sandbox/work`, запись (`KT1_OUT`, `HOME`) | всё, что пишет скрипт. После прогона — в выходной архив и в копию `work.saved/`; tmpfs снимается |
| `kernel/` | root, 0444 / 0555 | `/sandbox/kernel`, только чтение — **только d3-run** | замороженное ядро; `KT1_DIR=/sandbox/kernel/kt1` |
| `guard/` | root, 0444 / 0555 | `/sandbox/guard`, только чтение — только Python | копия `py_guard.py`, сумма — в журнале |
| `log/` | root, 0700 | **не монтируется** | доверенный журнал; вывод пишется сюда потоком |

**Что ещё видно в песочнице:**
- `/usr` только для чтения, с ссылками `/bin`, `/lib`, `/lib64`;

- свой `/proc` (своё пространство PID);
- `/dev` только для чтения;
- `/tmp` и `/dev/shm` в памяти, по 256 МиБ.

**Чего не видно:** `/etc`, `/home`, `/root`, `/var`, папок сессии, исходного архива ядра, журналов. Сети нет: только loopback.

## 2. Порядок прогона

1. **Входные файлы.** Нет файла — отказ (код 2). Сумма архива сверяется с суммой, которую зафиксировал Автор (`--sha`); не совпала — отказ.
2. **Проверка архива до распаковки** (§ 0, п. 3). Нарушение — отказ с причиной в журнале.
3. **Распаковка** в новую пустую `src/`, права только на чтение. Опись `src_before`.
4. **Только d3-run:** сумма ядра — с константой, проверка, распаковка в `kernel/`, опись `kernel_before`.
5. **`work/` монтируется** как tmpfs с квотой.
6. **Перед каждым запуском** — проверка, что от прежних прогонов не осталось процессов (§ 0а).
7. **Запуск без изменений в песочнице** (§ 3). Слои:
   - внешний — bubblewrap от nobody и пределы;
   - Node — `--permission`;
   - Python — `py_guard.py`.
8. **Во время запуска** оболочка:
   - пишет stdout и stderr потоком в `log/` до общего предела;
   - каждые 0,05 с проверяет свободное место в `work/` и срок.

   Превышение — немедленное снятие песочницы и статус `OUTPUT_LIMIT`, `WORK_LIMIT` или `TIMEOUT`. Остальные запуски прогона не делаются.
9. **После прогона:**
   - описи `src_after` / `src_unchanged`, для d3-run — `kernel_unchanged`;
   - опись `work/` и её объём;
   - итоговые статусы (§ 3а).
10. **Выходной архив** `<папка>-out.zip` (`log/` и `work/`) с sha256 передаётся без обработки. Код выхода оболочки — по § 3а.

## 3. Точная команда (пример, Python, режим a5)

```
setpriv --reuid=65534 --regid=65534 --clear-groups --no-new-privs --bounding-set=-all
  bwrap --unshare-all --die-with-parent --new-session --cap-drop ALL --clearenv
        --setenv PATH /opt/node22/bin:/usr/bin:/bin --setenv LANG C.UTF-8 --setenv HOME /sandbox/work
        --setenv KT1_OUT /sandbox/work --setenv KT1_RUN /sandbox --setenv KT1_READ /sandbox --setenv KT1_WRITE /sandbox/work
        --ro-bind /usr /usr --symlink usr/bin /bin --symlink usr/lib /lib --symlink usr/lib64 /lib64
        --proc /proc --dev /dev --size 268435456 --tmpfs /dev/shm --remount-ro /dev --size 268435456 --tmpfs /tmp
        --ro-bind <прогон>/src /sandbox/src --bind <прогон>/work /sandbox/work --ro-bind <прогон>/guard /sandbox/guard
        --remount-ro / --chdir /sandbox/src --uid 65534 --gid 65534
  prlimit --nproc=256 --nofile=512 --fsize=268435456 --cpu=1805 --as=8589934592 --
  timeout --kill-after=5 1800
  /usr/bin/python3.13 -I /sandbox/guard/py_guard.py a5/p.py
```

**`work/` перед запуском** монтируется оболочкой:
`mount -t tmpfs -o size=536870912,nr_inodes=20000,mode=0700,uid=65534,gid=65534,nosuid,nodev tmpfs <прогон>/work`.

**Отличия для Node:**
- добавляется `--ro-bind /opt/node22 /opt/node22`, `guard` не монтируется;
- внутренняя команда — `node --permission --allow-fs-read=/sandbox --allow-fs-write=/sandbox/work <вход> [аргументы]`.

**Для d3-run** добавляются `--ro-bind <прогон>/kernel /sandbox/kernel` и `--setenv KT1_DIR /sandbox/kernel/kt1`.

**Пределы по умолчанию** (все записываются в журнал, поле `limits`):

| Предел | Значение | Ключ |
|---|---|---|
| время по часам | 1800 с; процессорное — 1805 с; запасной срок снаружи — 1830 с | `--timeout` |
| адресное пространство | 8 ГиБ на процесс | `--mem` |
| stdout + stderr | 64 МиБ на весь прогон | `--max-output` |
| `work/` | 512 МиБ и 20 000 файлов и папок | `--work-quota`, `--work-files` |
| процессы / дескрипторы / файл | 256 / 512 / 256 МиБ | — |
| `/tmp`, `/dev/shm` | по 256 МиБ | — |

Пределы, отличные от умолчания, называются до прогона и попадают в журнал (`argv`, `limits`).

## 3а. Статусы и код выхода оболочки

| Код | `runner_status` | `test_status` | Значение | `protocol_complete` |
|---|---|---|---|---|
| 0 | `COMPLETED` | `EXIT_0` | все запуски завершились с кодом 0 | true |
| 1 | `COMPLETED` | `EXIT_NONZERO` | испытуемый скрипт завершился с ненулевым кодом (код — в `runs[].exit_code`) | true |
| 2 | `REFUSED` | `NOT_RUN` | отказ до запуска; причина — `refused` | false |
| 3 | `COMPLETED` | `TIMEOUT`, `OUTPUT_LIMIT`, `WORK_LIMIT` | превышен предел, запуск прерван, протокол неполный | false |
| 4 | `RUNNER_ERROR` | `NOT_RUN` | ошибка самой оболочки; причина — `runner_error`; журнал записывается | false |

- `COMPLETED` значит, что **оболочка** отработала до конца. Успех испытания этим не утверждается.
- `protocol_complete: true` значит, что вывод и `work/` получены целиком. О физическом или формальном результате скрипта это ничего не говорит.
- При нескольких запусках итог — худший: `OUTPUT_LIMIT` > `WORK_LIMIT` > `TIMEOUT` > `EXIT_NONZERO` > `EXIT_0`.

## 5. Ограничения

- **audit hook в Python — не железная граница** (замечание Грока). Граница — bubblewrap. Проба без `py_guard` это показывает.
- **Дочерние процессы на внешнем слое разрешены.** Они остаются в тех же пространствах имён и под теми же пределами. Запрещает их второй слой (`--permission`, `py_guard`).
- **Общего предела памяти на всю песочницу нет:** cgroup в контейнере не делегированы. Действуют:
  - адресное пространство на процесс;
  - число процессов;
  - объёмы `/tmp`, `/dev/shm` и `work/` — tmpfs, они занимают память не больше своих квот.
- **Признак `WORK_LIMIT`.** Квоту `work/` держит ядро Linux жёстко: записать сверх неё нельзя, скрипт получает ENOSPC. Признак выставляется, если свободно меньше 1 МиБ или меньше 16 файлов — сторожем во время запуска и проверкой после. Скрипт, получивший ENOSPC, освободивший место и завершившийся между двумя проверками, признак может не получить. Сам ENOSPC он при этом видел, и в его stderr это обычно отражено.
- **Предел вывода считается по прочитанным байтам.** Сколько скрипт пытался вывести сверх предела, точно неизвестно. Поэтому поле — «отброшено не меньше».
- **Свойство Node.js, не песочницы:** при выходе процесса незаписанный вывод в канал может теряться. Проверено без всякой песочницы: `node --check` с длинной строкой отдаёт в канал ровно 64 КиБ. Большие протоколы надёжнее писать файлами в `KT1_OUT` (§ 6).
- **`scan.txt` редакции 2 удалён.** Это была эвристика. Теперь ядро в режимах без ядра физически не смонтировано, а файлы ядра в архиве отвергаются.
- **Флаг `--permission` в этой форме проверен на Node.js v22.22.0.** На другой версии самопроверку нужно повторить до прогона.
- **`/etc` в песочнице нет.** Ошибки среды возвращаются как есть. `TZ` не задан, время — UTC.
- **Сама оболочка доверенная.** Она работает от root снаружи песочницы, в одноразовом облачном контейнере сессии. Чужой код выполняется только внутри песочницы от nobody.

## 6. Что нужно от скриптов, чтобы их не править

- **Один архив (`.zip`)** и одна строка запуска: язык, входной файл, аргументы. Ты называешь их при сдаче. Пути в архиве — из `[A-Za-z0-9._-]` и `/`.
- **Только встроенные модули Node.js или стандартная библиотека Python 3.13.** Внешних пакетов, сети и запуска процессов нет.
- **Чтение** — только своих файлов, относительно корня архива (это текущая папка).
- **Вывод** — в stdout / stderr или в файлы в папке `KT1_OUT` (Node: `process.env.KT1_OUT`; Python: `os.environ['KT1_OUT']`).
  - Протоколы и всё объёмное лучше писать **файлами** в `KT1_OUT` (Node — `fs.writeFileSync`), а в stdout выводить краткую сводку. Причина — § 5, свойство Node.js.
  - Если ожидаемый объём больше пределов § 3, назови нужные пределы при сдаче.
- **Код выхода:** 0 — скрипт отработал. Ненулевой код оболочка записывает как `EXIT_NONZERO` и не толкует. Что он значит, решаешь ты при разборе.
- **Д-3 — путь к ядру только через `KT1_DIR`:**
  - `KT1_DIR` — папка, где лежит `kt1.js`;
  - подключение: `require(path.join(process.env.KT1_DIR, 'kt1'))`;
  - зашитых путей и файлов ядра в архиве набора быть не должно.
- **А-5 — ядро не упоминается вовсе.**

## 7. Формат сдачи текстом (для упаковки)

Каждый файл — заголовок и сразу за ним блок кода:

    ### FILE: a5/check1_root.js
    ```js
    …содержимое файла…
    ```

- **Путь** — относительный, из сегментов `[A-Za-z0-9._-]`; без `.`, `..`, пустых сегментов, `\` и ведущего `/`; не длиннее 200 символов. Дубликаты без учёта регистра отвергаются.
- **Содержимое блока пишется в файл дословно**, с переводом строки в конце. Если внутри файла есть тройные обратные кавычки, ограждай блок четырьмя.
- **Только LF.** Текст с CR отвергается целиком.
- **Сборка** — `pack_from_text.py`:
  - порядок файлов — по пути, время фиксированное, без сжатия;
  - после сборки архив перечитывается и сверяется с текстом побайтно;

- **Автор сверяет** опись и архив с твоим опубликованным текстом и фиксирует сумму от своего имени.
- **Раздельно:** А-5 и Д-3 — два текста и два архива.
