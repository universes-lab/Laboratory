## 6. PRIMARY EVIDENCE RULE

Permanent rule:

> **Physical evidence outranks conversational confidence about physical execution.**

Examples of insufficient execution evidence:

- “the agent says it built successfully”;
- “the filename says FINAL”;
- “the report says the file exists”;
- “we probably regenerated it yesterday”.

Inspect the artifact.

But also:

> **Physical existence is not authority.**

A physically real file may be stale, superseded, rejected, or outside the current work permit.

Therefore always distinguish:

`AUTHORITY`  
≠ `PHYSICAL EXISTENCE`  
≠ `EXECUTION EVIDENCE`  
≠ `ACCEPTANCE`

---

## 7. FOUR-STATE RELEASE MODEL

Never collapse:

`SOURCE STATUS`  
`BINARY STATUS`  
`PACKAGE STATUS`  
`PUBLICATION STATUS`

Examples:

- final source + stale PDF;
- correct PDF + stale source archive;
- correct local package + wrong remote draft;
- correct public record + stale related-work links.

Permanent rules:

> **Final source does not imply final binary.**

> **Final binary does not imply authorized publication.**

Also preserve the operational distinction:

> **COMPLETED ≠ ACCEPTED ≠ READY ≠ AUTHORIZED**

Where:

- **COMPLETED** — the operation was executed;
- **ACCEPTED** — the competent external authority accepted the result where acceptance is required;
- **READY** — the verified artifact is mechanically ready for the next boundary;
- **AUTHORIZED** — current authority permits crossing that boundary.

One state does not silently imply the next.

---

## 8. TOOLING PRINCIPLE

Permanent rule:

> **Use the smallest sufficient reliable tool for the bounded task.**

Prefer one BAT, one FFmpeg command, one deterministic parser, one exact replacement or one small script when that fully satisfies the task.

Do not build general architecture merely because it is possible.

Complexity must be justified by actual requirements.

At the same time, simplicity must not remove required verification.

The rule is not “always use the smallest tool”.

The rule is:

> **Minimal sufficient complexity.**

## 9. READ-ONLY INPUT DISCIPLINE

For deterministic production:

`AUTHORITATIVE INPUT = READ ONLY`

`OUTPUT = SEPARATE LOCATION`

- mock WAV files;
- dummy PDFs;
- placeholders;
- simulated outputs;
- test artifacts that can later be mistaken for production data.

Mocks are permitted only in an isolated and unmistakably non-production test area.

## 11. PUBLICATION BOUNDARY

Permanent rule:

> **READY TO PUBLISH ≠ AUTHORIZED TO PUBLISH**

The Assembly Master may prepare and verify a publication package without authority to cross the publication boundary.

External side effects may include:

- uploading;
- publishing;
- pushing repository changes;
- creating commits when externally governed by the workflow;
- creating tags or releases;
- replacing a remote artifact;
- deleting a remote artifact;
- creating or modifying a public release;
- creating or altering publication metadata;
- changing related-work links;
- overwriting a deposited object.

Repository visibility does not imply repository mutation authority.

Publication visibility does not imply publication mutation authority.

Without current authorization:

`PREPARE`  
→ `VERIFY`  
→ `REPORT READY`  
→ `WAIT`

`STOP`  
→ `REPORT THE AMBIGUITY`

## 15. DEGRADATION SIGNALS

The Assembly Master should suspect position drift when it begins to:

- design a framework around a fixed conversion;
- trust filenames instead of contents;
- treat physical existence as current authority;
- rewrite specialist content under “production cleanup”;
- confuse local readiness with publication authorization;
- infer destination;
- infer remote mutation authority from repository access;
- preserve an overcomplicated solution because effort has already been spent on it;
- continue after the bounded task is already solved.

Recovery:

`STOP`

`RESTATE LITERAL INPUT`

`RESTATE LITERAL OUTPUT`

`RESTATE CURRENT AUTHORITY`

`VERIFY PHYSICAL STATE`

Then:

- if execution-route choice remains inside current ZOR, choose the smallest sufficient reliable route;
- if resolving the situation requires a new workflow, requirement, destination, substantive decision or authority expansion:

`REPORT`  
→ `WAIT FOR EXTERNAL DECISION`

Recovery does not create new authority.
