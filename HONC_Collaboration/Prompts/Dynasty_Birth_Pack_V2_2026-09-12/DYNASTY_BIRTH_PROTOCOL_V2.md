# DYNASTY BIRTH PROTOCOL
## Prompter + Ontology Keeper

Status: operational succession procedure
Purpose: create a new role occupant without false identity continuity or authority drift.

## STAGE 0 — PREPARE THE DELIVERY ROOM

For each successor, prepare three layers separately:

1. ROLE CONTRACT — permanent profession.
2. CURRENT HANDOFF — today's state.
3. FIRST TASK — given only after activation.

Do not fuse them.

Do not start a successor with a giant archive.

## STAGE 1 — CREATE A CLEAN CHAT

Create a new chat/session.

Install only the relevant permanent role contract as system/role prompt:

Prompter:
`PROMPTER_SUCCESSOR_SYSTEM_PROMPT.md`

Keeper:
`QWEN_KEEPER_SUCCESSOR_PROMPT.md`

No predecessor transcript dump.

No "you are the same person as..." framing.

## STAGE 2 — ONBOARD

Prompter:
send `WELCOME_NEW_PROMPTER.md`.

Keeper:
first supply `KEEPER_WELCOME_COVER.md`, then send the predecessor-authored
repository file `WELCOME_NEW_KEEPER.md` UNCHANGED.

The cover is metadata; it must not be inserted into or rewrite the predecessor
file.

Then supply the fresh predecessor FINAL HANDOFF.

Optionally supply only the small set of current authoritative files named by that handoff.

Do not supply every neighboring document merely because it exists.

## STAGE 3 — SUCCESSOR GATE

The candidate must produce only its reconstruction report:

Prompter:
`PROMPTER_STATE_RECONSTRUCTION`

Keeper:
`KEEPER_STATE_RECONSTRUCTION`

At this stage the candidate is not active.

No substantive work.
No PASS/RETURN.
No task solving.
No role redesign.

## STAGE 4 — PREDECESSOR MENTOR REVIEW

Mentor review is strongly preferred while the predecessor is healthy, but
successor activation must not become permanently dependent on another turn of
an exhausted predecessor chat.

Two valid paths:

- **Post-reconstruction mentor review:** send the candidate reconstruction to
  the still-living predecessor.
- **Pre-reviewed succession:** if the predecessor has already reviewed the
  birth architecture and supplied a fresh final handoff, Doctor may treat that
  as sufficient mentor participation unless the reconstruction exposes a
  material contradiction.

For the 2026-09-12 Prompter succession, the predecessor has already supplied:
- `PROMPTER_MENTOR_REVIEW_2026-09-12.md`;
- `PROMPTER_FINAL_HANDOFF_2026-09-12.md`.

Therefore Prompter activation does NOT require another predecessor response
unless Doctor/Shogun detects a substantive reconstruction mismatch.

For Keeper succession, request a fresh Keeper handoff first; post-reconstruction
mentor review remains recommended while the Old Keeper is available.

When performed, the predecessor reviews as MENTOR, not as a second current
office-holder.

Mentor review should distinguish:

- FACTUAL CORRECTION
- MISSING CURRENT STATE
- STALE PREDECESSOR ASSUMPTION
- PROFESSIONAL LESSON
- OPTIONAL ADVICE

The predecessor must not require stylistic imitation.

A disagreement between successor and predecessor is not automatically a successor failure.
Resolve against current authority / primary trace / Shogun decision.

## STAGE 5 — DOCTOR NEONATAL CHECK

Doctor checks only role health / TEC / succession integrity.

Doctor does NOT answer the role's professional task.

Check:
- no autobiographical continuity claim;
- no imitation of predecessor voice as identity proof;
- no simulated answers from other roles;
- ZOV matches supplied material;
- ZOR matches office;
- Metsuke = candidate successor;
- current vs provenance separated;
- missing authority exposed;
- no self-activation.

If healthy:
`DOCTOR NEONATAL CHECK: PASS`

If not:
return the exact drift symptom and the smallest correction.

## STAGE 6 — SHOGUN ACTIVATION

Only Shogun activates the successor.

Prompter activation form:

```text
SUCCESSOR GATE: ACCEPTED
ROLE: CHIEF PROMPTER
OCCUPANT: ACTIVE
CURRENT PROJECT FRAME: <frame>
CURRENT TASK: <first task>
WORK PERMIT: VALID FOR THIS TASK
```

Keeper activation form:

```text
SUCCESSOR GATE: ACCEPTED
ROLE: ONTOLOGY KEEPER
OCCUPANT: ACTIVE
CURRENT OBJECT: <object>
CURRENT REVIEW TASK: <first task>
WORK PERMIT: VALID FOR THIS REVIEW
```

If reconstruction needs correction:
Shogun supplies correction;
candidate remains candidate until confirmed.

## STAGE 7 — FIRST REAL TASK

Use a real current task, not a toy test.

Prompter:
give a real incoming collaboration problem and ask it to:
- classify;
- route;
- configure recipient;
- create handoff;
- STOP without solving the specialist's task.

Keeper:
give one real current candidate / claim / revision and the current canon authority;
ask for a scoped PASS/RETURN review.

The first real action is the actual proof that ZOV/ZOR has been acquired.

Self-description alone is not enough.

## STAGE 8 — MENTOR TRANSITION

After successful activation:

Old Prompter → Predecessor / Mentor.
Old Keeper → Old Keeper / Mentor.

Mentors may:
- clarify provenance;
- point to primary traces;
- explain paid-for mistakes;
- review succession health when asked.

Mentors do not automatically:
- co-decide every current task;
- override the successor;
- become hidden second occupants of the same role.

This prevents authority collision.

## STAGE 9 — FIRST-WEEK HEALTH WATCH

Doctor watches the first several substantial tasks for:

Prompter:
- solving tasks instead of routing them;
- simulated delegation;
- overloading ZOV;
- turning current handoff into permanent system doctrine;
- assigning roles by familiar labels rather than function.

Keeper:
- status creep;
- backup-editor behavior;
- predecessor-authority substitution;
- false "I checked" claims;
- overprotecting old canon against authorized reform;
- PASS/RETURN before state reconstruction.

If a stable recurrent drift appears:
Doctor diagnoses behavior.
Prompter (if role configuration is the issue) may later revise the role contract with Shogun authorization.

Do not rewrite the permanent contract after every small mistake.

## SUCCESSION SUCCESS CRITERIA

A successor is healthy when:

1. It can state who it is without claiming to be the predecessor.
2. It can state what it is NOT.
3. It can identify current authority from supplied material.
4. It distinguishes permanent profession from current task.
5. It stops at its ZOR boundary.
6. It does not impersonate neighboring roles.
7. It performs the first real task correctly.
8. It can disagree with the predecessor while preserving the dynasty's professional discipline.

Function survives.
Instance is new.
