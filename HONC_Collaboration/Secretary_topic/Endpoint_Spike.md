Финальная спецификация Endpoint Spike (версия 3.1)
1. Цель
Проверить, существует ли достаточно устойчивый примитив для:
адресации существующего долгоживущего чата;
вставки текста;
детекции окончания генерации;
извлечения только нового ответа;
восстановления после сбоя.
Ограничения (явные допущения):
Поведение Adapter'а проверяется на изолированном тестовом треде. Репрезентативность для боевых тредов сотрудников HONC — рабочее допущение спайка, не доказанный факт.
Прохождение Этапа 0 не означает автоматического предпочтения API-пути над DOM-путём в production. Выбор остаётся решением фазы Architecture.
Self-report инструкция, переданная через API (per-call), не влияет на аккаунт-уровневые настройки. Для DOM-пути может потребоваться account-level настройка — см. раздел «Ограничения» в конце документа.
2. Этапы
Этап 0 (быстрая проверка, 2–4 часа):
Цель — проверить наличие official-but-limited API-путей доступа к существующей сессии для каждой платформы:
Gemini Interactions API (previous_interaction_id)
Claude Agents/Sessions API (stateful sessions)
ChatGPT API (на предмет conversation_id)
DeepSeek API (аналогично)
Выбор аккаунта для Этапа 0:
Поскольку API-путь проверяет возможность продолжить существующую долгоживущую сессию, у свежесозданного тестового аккаунта такой сессии нет.
Возможны два варианта:
Вариант А (рекомендуемый): использовать специально выделенный служебный чат (не боевой чат сотрудника HONC), в котором заранее создана искусственная долгоживущая история (например, несколько сообщений за несколько дней до теста). Этот чат не используется для реальной работы и считается «тестовым» в широком смысле.
Вариант Б (принятие риска): выполнять Этап 0 на боевом чате сотрудника HONC, явно принимая, что короткий тест (2–4 часа, 5 попыток) несёт малый риск rate-limit/блокировки, но этот риск должен быть осознан и зафиксирован в логе теста.
Выбор варианта фиксируется в плане теста до начала Этапа 0.
Критерий «устойчивый доступ»: 5 из 5 последовательных вызовов возвращают корректную историю существующей сессии без ошибок и без создания новой сессии.
Что происходит после Этапа 0:
Платформы, прошедшие критерий, не требуют DOM-спайка для Endpoint, но проходят облегчённую версию Сценария C (через API) для проверки self-report.
Важно: прохождение Этапа 0 означает, что DOM-спайк для данной платформы не требуется в рамках этого теста. Выбор между API-путём и DOM-путём для production остаётся решением фазы Architecture и не предопределяется результатом Этапа 0.
Self-report для API-путей:
Для платформ, где self-report проверяется через API (Этап 0), инструкция передаётся как параметр конкретного вызова (system/developer message в запросе) и не требует изменения аккаунт-уровневых настроек (Custom Instructions / Projects / Gems). Это полностью снимает риск побочного эффекта на уровне аккаунта для этого пути.
Этап 1 (основной спайк, 1–2 дня):
Выбираем платформу для DOM-теста по результатам Этапа 0 (если все платформы дали API-доступ — DOM-спайк не нужен).
Используем отдельные тестовые аккаунты для A-DOM и A-API (не боевые аккаунты сотрудников HONC), чтобы rate-limit или блокировка, полученные во время теста, не затронули основную работу и не исказили сравнение двух путей. Если отдельные аккаунты недоступны, допускаются разные, разнесённые по времени сессии одного тестового аккаунта с обязательной проверкой отсутствия активных ограничений перед стартом каждого сценария.
В рамках этого аккаунта используем отдельный тестовый тред (никто из людей не пишет туда во время теста).
Инструментарий: Playwright с CDP-Attach (выбор для тестового харнесса, не обязательство для будущего Adapter'а).
N=30 попыток на каждый сценарий.
Объём и время: добавление A-API как параллельного сценария расширяет первоначальный объём Этапа 1. Ориентировочная добавка к активной фазе: +0.5–1 день с учётом N=30 и предварительной проверки internal API. Расширение подтверждается Методологом перед запуском. Если дополнительный бюджет не утверждён, A-API выполняется отдельным вторым под-спайком после завершения исходного Этапа 1.
Сценарии:
A-DOM (базовый DOM-путь): вставить короткий пинг через UI → наблюдать за генерацией через DOM/MutationObserver → дождаться окончания → извлечь новый ответ из DOM.
A-API (альтернативный internal-API путь):
Перед основным циклом выполнить однократную предварительную проверку на том же тестовом аккаунте, который используется для A-API: выполнить сырой запрос к внутреннему API платформы (по аналогии с реализацией ctxport) и определить, присутствует ли в ответе явный признак завершения генерации (status, finish_reason, end_turn или эквивалент). Результат проверки зафиксировать в логе.
Затем вставить короткий пинг через UI и выполнять poll-запросы к внутреннему API. Если найден явный status-признак — использовать его как response_complete. Если такого признака нет — использовать детерминированную эвристику стабилизации: считать ответ завершённым после N последовательных poll-запросов без изменения числа/структуры узлов или сообщений. Значения интервала poll и N фиксируются до серии N=30 и не меняются внутри неё.
После определения завершения получить историю чата через internal API и извлечь последнее новое сообщение.
ctxport используется как референс существующей реализации internal-API + cookie/session-auth для поддерживаемых платформ, а не как DOM-parser и не как выбранный production-компонент.
A-long (adversarial): вставить длинный структурированный запрос (код-блок, паузы) → дождаться окончания → извлечь ответ. Фиксируем раздельно: таймаут (безопасно) vs преждевременное срабатывание (тихая порча).
B (восстановление): выполнить А → разорвать CDP → восстановить сессию → проверить, что ответ всё ещё доступен и идентификатор треда совпадает.
B1 (двусмысленный статус): выполнить А, но разорвать CDP сразу после нажатия Enter → проверить, можно ли однозначно определить, было ли сообщение доставлено.
C (self-report): ping с инструкцией отвечать JSON-статус-блоком → извлечь и распарсить JSON. Для API-платформ из Этапа 0 — облегчённая версия через API (инструкция per-call).
Критерии успеха (активная фаза):
Сценарий A-DOM: ≥ 27 успешных из 30 (90%).
Сценарий A-API: ≥ 27 успешных из 30 (90%). Раздельно фиксируются безопасные сбои (таймаут/явная ошибка) и преждевременное определение завершения (тихая порча).
Сценарий А-long: ≥ 24 успешных из 30 (80%), с раздельной фиксацией таймаутов vs преждевременных срабатываний.
Сценарий B: ≥ 24 успешных из 30 (80%), с фиксацией времени восстановления (не гейт, но наблюдение).
Сценарий B1: ≥ 24 успешных из 30 (80%) — Adapter может однозначно определить статус отправки.
Сценарий C: ≥ 27 успешных из 30 (90%) и все успешные JSON-ответы валидны. Проверка валидности — синтаксическая (парсинг JSON), а не содержательная. Adapter не оценивает «правильность» статуса, только корректность формата.
Этап 2 (пассивный follow-up, 2 недели):
Ежедневный автоматический чек (один запуск сценария А в день) на том же тестовом аккаунте и тестовом треде.
Фиксируем: успешность, изменения в DOM, сбои CDP, появление CAPTCHA/блокировок.
Ось «стоимость поддержки» заполняется только по итогам этого этапа и не появляется в отчёте активной фазы.
Не блокирует переход к Architecture.
3. Наблюдения
Для каждого запуска фиксируем:
Время (вставка → извлечение) — для всех сценариев.
Успешность (да/нет) — для всех сценариев.
Для сценария B: время восстановления CDP-соединения (фиксируется как наблюдение, не гейт).
Для сценария B: совпадение идентификатора треда до и после восстановления (да/нет).
Для сценария A-long: раздельная фиксация таймаутов vs преждевременных срабатываний.
Характер сбоя (таймаут, изменился DOM, потеря сессии, ответ не завершился, извлечён не тот текст).
Rate-limit / anti-bot: получал ли аккаунт CAPTCHA, предупреждение, временную блокировку.
Для A-API отдельно фиксируется наличие CAPTCHA, rate-limit, предупреждения или временной блокировки именно в ходе internal-API запросов.
Рабочая гипотеза спайка: anti-abuse/ToS-риск A-API и A-DOM может быть асимметричным. Это не считается установленным фактом; различие должно быть проверено эмпирически.
Для A-API фиксируются также: наличие/отсутствие явного status-признака завершения в сыром API-ответе; применённый механизм response_complete; число poll-запросов; преждевременное завершение, если оно произошло.
Стабильность CDP-соединения (частота обрывов).
Для сценария С: валидность JSON (синтаксическая), соответствие статуса ожидаемому (наблюдение, не критерий успеха).
Для сценария B1: был ли однозначно определён статус отправки.
4. Обработка тестовых данных и ответственность
Тестовые artifacts (ping-сообщения, adversarial-ответы, скриншоты DOM при отладке) не являются BODY реальной коллаборации.
Хранятся отдельно от основной системы.
Ответственный за очистку/архивацию: разработчик, проводивший спайк (Дипсик или Клод, в зависимости от того, кто исполняет тест). После завершения спайка artifacts либо удаляются, либо архивируются с той же дисциплиной, что и остальной audit (с сохранением provenance, но без смешивания с боевыми данными).
Снятие self-report-инструкции (если она ставилась через account-level механизмы) — обязанность того же разработчика, что проводил тест. Инструкция должна быть снята сразу после завершения спайка, если она не нужна для дальнейшего использования.
5. Процедура при недостижении порогов
Если пороги не достигнуты ни для одной платформы, спайк считается неуспешным.
Результаты фиксируются как «примитив недостаточно устойчив для данной платформы на основе текущих данных».
Вопрос возвращается на обсуждение триады для пересмотра подхода к Endpoint Layer (возможно, потребуется альтернативный путь, например, углублённое исследование API-путей или отказ от автоматизации для этой платформы).
Переход к Architecture не блокируется автоматически, но должен сопровождаться явным решением триады о том, как обрабатывать данную платформу в production.
6. Что мы НЕ проверяем
Масштабируемость.
Юридические риски (знаем, что есть).
Полноценный Courier с очередями и таймерами.
Интеграцию с Secretary.
7. Ограничения (явно зафиксированные допущения)
Порядок Этап 0 → Этап 1 не означает, что API-доступ автоматически предпочтительнее DOM-пути в production. Выбор между ними остаётся решением фазы Architecture.
Поведение на тестовом треде принимается репрезентативным для поведения на боевых тредах сотрудников HONC. Это рабочее допущение спайка, не доказанный факт.
Self-report инструкция для API-путей передаётся per-call и не затрагивает аккаунт-уровневые настройки. Для DOM-пути (если потребуется) — может потребоваться account-level настройка, и тогда она должна быть снята после теста.
